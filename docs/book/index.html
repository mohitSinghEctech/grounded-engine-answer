1What this project is, and why contents

A service that answers questions about Indian income tax law using only the text of the Acts it has been given, cites the provision behind every claim, and declines rather than guessing. The interesting part is not that it answers. It is that it can be caught when it does not.

1.1Two Acts in force at once

India has two income tax statutes that both matter right now. The Income-tax Act, 1961 governed for sixty-five years. The Income-tax Act, 2025 replaced it with effect from 1 April 2026. The 1961 Act is not merely history: it still governs every financial year up to and including 2025-26, which means assessments, appeals and disputes will run on it for years.

And the 2025 Act renumbered everything. Not adjusted — renumbered. The old Act grew by accretion for six decades, so it had 80C, 80-IA, 115JD: numbers with letters glued on, because Parliament kept inserting sections between existing ones. The new Act is a clean 1 to 536. The consequence is brutal for a question-answering system:

So the retrieval layer cannot just find text that looks relevant. It has to know which Act governs the year the question is about, and it has to keep provisions from the wrong Act out of the answer entirely. That single requirement is why this project has a tax-year filter, why the eval set has a whole year-scoped category, and why one of the required scores is act_correct = 1.00: a wrong Act is wrong law, not a near miss.

1.2What “grounded” means

Jargon
Grounded
An answer is grounded when every factual claim in it can be traced back to a specific piece of source text that was shown to the model in this request. Not “the model knows this” — this paragraph, right here, says it.
RAG — retrieval-augmented generation
The pattern: instead of asking a language model what it remembers, you first retrieve relevant source text from your own documents, paste it into the prompt, and ask the model to answer from that. The model becomes a reader and a writer rather than a memory.

Grounding is the whole product. A general-purpose model will answer a tax question confidently and be wrong in a way nobody can check: the answer is prose, the reasoning is invisible, and the reader has no thread to pull. This service produces something different — an answer plus a list of citations, where the citations are not decoration. They are verified after the fact against the exact provisions the model was handed. If the model cites a section it was never given, that reference is pulled out of the citation list, reported separately as an unsupported_citation, and logged as a warning.

That is the difference between saying “please cite your sources” and building a system where citing a source is a checkable claim.

1.3What the project claims, and what it does not

It claims, and can demonstrate on a 40-question set:

  • It finds the right provision for 26 of the 28 questions where a specific section is expected — and finds it on every run, not on a lucky one.
  • It cites only provisions from the correct Act for the year asked about, on 97–98% of applicable questions.
  • It declines when it should decline, on 36–38 of 40 questions.
  • It answers correctly, judged by hand against the corpus, on 34 of 40.

It does not claim:

  • To be tax advice. Prompt rule 3 forbids recommending an option or computing a liability, and the refusal path enforces it. This is a statutory lookup tool, not an adviser.
  • To be current. The corpus is a snapshot dated 2026-09-14, and some of it is older text than that — s.80C in the corpus still reads “one lakh rupees”, which is pre-2014 law. The system's job is to report its corpus faithfully, and the corpus date travels back with every answer so a caller knows how stale it is (see 7.6).
  • To cover all of Indian tax. No GST, no stamp duty, no rates beyond what the department's own guidance pages carry.

2Vocabulary contents

These are the words for things already built in this repository. Each definition ends with a pointer to the file where you implemented it, because the fastest way to fix a vocabulary gap is to see the word attached to code you already wrote.

2.1Retrieval words

Jargon
Embedding
A list of numbers that represents the meaning of a piece of text. Two texts about the same idea get lists that are close together; two unrelated texts get lists that are far apart. You get one by sending the text to an embedding model.
Here: OpenAICompatibleEmbedder.embed in services/tax-agent/app/retrieval/embedders.py.
Vector
The list of numbers itself. An embedding is a vector; the word “vector” is just the mathematical name for an ordered list of numbers you can measure distances between.
Dimensions
How long that list is. This project uses text-embedding-3-small, which produces 1,536 numbers per text. The number matters only because it must match on both sides: text embedded with a 1,536-dimension model cannot be searched with a 768-dimension one. It does not error — it returns confident nonsense, which is worse.
Here: embedding_dims in config.py, and VectorStore.verify(), which refuses to start the service if the index and the embedder disagree.
Vector database / vector store
A database that stores vectors and can quickly find the ones nearest to a query vector. Qdrant is the one used here. Every vector is stored alongside a payload — ordinary JSON metadata (act, section number, title, tax years, the text itself) that comes back with the result.
Here: retrieval/stores.py.
Chunk
A piece of a document small enough to embed usefully. You cannot embed a 500-page Act as one vector — it would mean nothing. So the Act is split. This corpus has 3,286 chunks over 1,423 sections, so the average section is two or three chunks and a long one is many more.
Here: corpus-builder/corpus/chunking.py.
Similarity score
A number saying how close a stored vector is to the query vector. This project uses cosine distance, so the score runs roughly 0 to 1 and higher is closer. In practice a genuinely relevant provision scores around 0.6–0.7 here; anything under 0.30 is discarded as noise (4.4).
Top-k
How many results you keep. retrieval_top_k = 6: six provisions go into the prompt. The “k” is just the mathematician's letter for “however many you asked for”. Small k risks missing law; large k dilutes the prompt and costs tokens.
Over-fetch
Asking the database for more than you intend to keep, because later filtering will throw some away. Here retrieval_over_fetch = 4, so a top-k of 6 fetches 24 candidates.
Hybrid search
Combining meaning-based (vector) search with word-based (keyword or lexical) search, because each fails where the other works. Vector search cannot find “section 139”; exact matching cannot find “the bit about late filing”. This project does not implement full hybrid search — it implements the specific half it needed: an exact payload lookup on section_number when the question names one (4.5).
Reranking
Taking the candidates the vector search returned and re-ordering them with a second, slower, more accurate model before choosing the top few. Not used here. The per-section cap is a cheaper, dumber substitute for part of what a reranker does.
MMR — maximal marginal relevance
A selection rule that trades a little relevance for diversity: after picking the best result, prefer the next result that is relevant and unlike what you already picked. It exists to stop near-duplicate passages filling the window. That is exactly the disease described in 8.6; the per-section cap treats the same symptom with one line of bookkeeping instead of a similarity matrix.
Grounding / citation verification
Checking, after the model has written its answer, that every reference it made is to a provision that was actually supplied. Anything else is a fabrication.
Here: split_citations in app/prompt.py.

2.2Structure words

Jargon
Interface
An agreed list of what something can do, with no statement of how it does it. “Anything that can embed(text) and knows its own dimensions” is an interface.
Protocol (Python)
Python's way of writing an interface down without inheritance. You declare a class with method signatures and no bodies; any object with matching methods satisfies it automatically, with nothing to inherit from and nothing to register. Type checkers verify the match; the runtime never needs to care. This is called structural typing, or informally duck typing with a paper trail.
Here: Embedder and VectorStore in retrieval/base.py; LLMGateway and Retriever in services/base.py; LLMClient in the gateway.
Adapter
A small class whose only job is to make one specific outside thing (a vendor SDK, a database client) fit an interface your code defined. QdrantStore is an adapter: it translates a VectorQuery into Qdrant's filter objects and translates Qdrant's points back into Hits. All the Qdrant-specific knowledge in the service lives in that one class.
Dependency injection
Instead of a function reaching out and creating what it needs, the thing it needs is handed to it. The /ask handler does not build a retriever; it receives one via Depends(get_retriever), and that retriever was built once at startup. Benefits: one client instead of one per request, and tests can hand over a fake.
Here: app/dependencies.py and the lifespan function in app/main.py.
Lifespan
FastAPI's hook for “do this once when the app starts, and this once when it stops”. Where the HTTP client, the embedder and the store are created, verified and later closed.
Registry
A dictionary from a name to a factory function, so a configuration string can select an implementation. EMBEDDERS["openai"], STORES["qdrant"], VENDORS["gemini"]. Adding a provider becomes adding a dictionary entry rather than editing the code that uses it — and an unknown name raises at startup, where it fails the container's health check, instead of on the first real request.
Refactor
Changing how code is arranged without changing what it does. The word is worth being strict about: if behaviour changes, it was not a refactor, it was a change. Section 10.7 is about how this project proves a refactor was behaviour-neutral rather than asserting it.
Idempotent
Safe to do twice. Re-running the parser replaces that Act's rows rather than adding a second copy; re-indexing writes the same point IDs so it overwrites rather than duplicates. Idempotence is what makes it comfortable to re-run a pipeline while tuning it.
Here: storage.write deletes the act's rows first; vectorstore.point_id derives a stable UUID from act/strategy/section/block/part.

2.3Measurement words

Jargon
Eval (evaluation set)
A fixed list of inputs with known expected outcomes, used to turn “it seems better” into a number. Here: 40 questions in eval/questions.yaml.
Harness
The program that runs the eval: sends every question, collects every answer, scores what can be scored automatically, and writes a row per question. eval/run.py.
Fixtures
The prepared inputs and fakes a test uses, so it runs the same way every time with no network. services/*/tests/conftest.py holds them; the gateway's tests never call a real model, which is why CI needs no API key.
Ground truth
The known-correct answer you compare against. For each eval question that is expected_sections, expected_acts, should_refuse. A question whose ground truth is wrong is worse than no question at all, because it will punish correct behaviour — which happened three times (8.8).
Baseline
The measured starting point that later work is compared against. eval/runs/baseline.csv. Without one, an improvement is an opinion.
Regression
Something that used to work and no longer does. The reason to keep running the whole eval rather than only the questions you were trying to fix.
Signal
One measurable property scored per question — retrieval_hit, act_correct, and so on. Six of them here. Keeping them separate is what lets you say which thing got better.
Denominator
What a rate is divided by. “24/28” is not “24/40”: only 28 of the 40 questions name an expected section, so only 28 can be scored for retrieval_hit. Getting the denominator wrong is the easiest way to accidentally flatter yourself, which is why non-applicable signals stay None (7.4).
Reproducible
Someone else, or you in three months, can re-run it and get the same thing. Threats to it here: the model (non-deterministic), the corpus (must be pinned — hence data/manifest.json with source URLs and hashes), and the grading rubric (grade against the corpus, never against your own tax knowledge, or the score is unrepeatable).
Variance
How much a measurement moves when nothing has changed. Measured here: retrieval_hit ranged 75%–86% across seven runs of near-identical configurations. Any observed difference smaller than the variance is not a result. This is the single most important idea in the book; it gets chapter 9.

2.4Transport and reliability words

Jargon
SSE — Server-Sent Events
A way for a server to push a stream of updates to a client over one ordinary long-lived HTTP response. The body is plain text: an event: line, a data: line, a blank line, repeat. One direction only, which is simpler than a WebSocket and is all this needs.
Here: Step.to_sse() in app/progress.py.
Token
The unit a language model reads and writes — roughly a word piece, about four characters of English. Billing and limits are counted in them. A typical request here is about 3,000 prompt tokens and writes fewer than 300.
TTFT — time to first token
How long between sending the prompt and the first output token arriving. Measured here as nearly the whole cost of a request: one sample spent 21.4 seconds to emit 27 tokens. Generation speed was never the problem; waiting to start was.
CORS — cross-origin resource sharing
The browser rule that a page served from one origin cannot call an API on a different origin unless that API sends headers permitting it. Relevant the moment a web UI on localhost:3000 calls this service on localhost:8080: the service will need CORS headers. Not configured yet — an honest open item, not a feature.
Rate limit / HTTP 429
The provider refusing a request because you have made too many, or used too much quota. Status 429, often with a Retry-After header saying how long to wait. Handled at two layers here (8.10).
Exponential backoff
Waiting longer after each successive failure — 0.5s, 1s, 2s — instead of hammering a service that is already struggling.
Here: calculate_retry_delay in services/llm-gateway/app/retry.py.
Jitter
Adding a small random amount to each backoff delay, so that many clients failing at the same moment do not all retry at the same moment and re-create the outage. Here: a uniform random 0–25% added on top of the computed delay.
Retry budget
A hard ceiling on total time spent retrying, checked before each sleep, so a slow failure cannot outlive the caller's patience. MAX_RETRY_TIME_SECONDS=60.
Timeout ladder
Nested timeouts arranged so each outer layer allows more time than the layer it wraps. Model 60s < gateway 75s < harness 90s. Get the order wrong and the outer layer gives up first, reporting a timeout from a place that was not actually waiting (12.6).
Request ID
A single identifier attached to one request and carried through every log line and every downstream call, so one user-visible failure can be traced across services. Accepted from the client as X-Request-ID or generated, then forwarded from tax-agent to llm-gateway by an httpx event hook.

2.5Tax words this codebase uses

Jargon
FY and AY
The financial year is the year income is earned: FY 2026-27 runs 1 April 2026 to 31 March 2027. The assessment year is the following year, when that income is assessed: AY 2027-28. They refer to the same income. This codebase stores the starting calendar year of the FY, so both “FY 2026-27” and “AY 2027-28” resolve to 2026. That conversion is the single most common off-by-one in Indian tax software and it is handled in exactly one place: app/tax_year.py.
Act code
This project's label for a source: ITA-1961, ITA-2025, DEPT-GUIDANCE. It is the first half of every citation, and it is what keeps guidance from being quoted as statute.
Statute against guidance
The Acts are law. The Income Tax Department's web pages are the department explaining the law in ordinary language — which return to file, what the slabs are. Both are in the index; they are labelled differently so an answer can never present guidance as law, and every guidance chunk carries the department's disclaimer inside its own text.
ITR
Income Tax Return — the actual form. ITR-1 (Sahaj) for simple salaried cases, ITR-2 where there are capital gains, ITR-6 for most companies. Only the guidance pages mention these; the Acts do not. Which is why procedural is its own eval category.
Section, sub-section, clause, proviso, schedule
A section is a numbered provision. Inside it, sub-sections are (1), (2); clauses are (a), (b); a proviso is a sentence beginning “Provided that…” that carves an exception. Schedules are tables and lists at the end of the Act, stored here as SCH-XV and friends. Sub-section boundaries matter to the code: they are the joints the chunker cuts at (6.4), because cutting anywhere else severs a provision from its own conditions.

3The architecture contents

Three processes that run in containers, one program that never does. Each boundary exists because something on the other side of it changes independently.

3.1Three services and one local builder

Read that diagram as four independent things, each with its own reason to exist:

Qdrant — the index
An off-the-shelf vector database, run from the published image qdrant/qdrant:v1.16.1. It holds all 3,286 chunks of both Acts and the guidance pages in one collection, ita_sections, with payload indexes on act, strategy, section_number, tax_year_from and tax_year_to. Its storage lives in a named Docker volume, so make down keeps the index and only make clean destroys it. One collection holds both Acts on purpose: which Act answers a question is decided by the tax-year filter, not by choosing a different collection.
llm-gateway — the model boundary
A small FastAPI service whose entire job is “send this prompt to a chat model and give me back text plus token counts, or a well-named error”. It owns retries, exponential backoff with jitter, the retry time budget, and the per-vendor request shaping. It knows nothing about tax.
tax-agent — everything interesting
Resolves the tax year, embeds the question, searches, filters, caps, assembles the prompt, calls the gateway, verifies the citations, and decides whether the result counts as an answer at all. It is the service this book is mostly about.
corpus-builder — local only
Turns the two Act PDFs and the seven scraped guidance pages into data/corpus.db and then into Qdrant points. It is not in docker-compose.yml, has its own requirements.txt, and is run by hand from the Makefile. Building the corpus costs money (about three cents of embeddings) and takes minutes; serving a question costs a fraction of a cent and takes three seconds. Those are different jobs with different lifecycles, so they are different programs.

3.2Why the gateway is a separate service

The honest one-line version: llm-gateway is the only thing that makes a chat-completion call. Everything about talking to a language model — the API key, the SDK, the retry policy, the error vocabulary, and the fact that different vendors reject different parameters — is behind one HTTP boundary.

Four concrete payoffs:

  1. Vendor differences stop leaking. Two real incompatibilities forced the abstraction, both confirmed against live APIs. reasoning_effort is accepted by every Gemini model and rejected outright by gpt-4.1-mini — “Unrecognized request argument supplied: reasoning_effort”, HTTP 400 on the very first call, because it had been passed unconditionally. And reasoning models want max_completion_tokens while chat models take max_tokens. Sending the wrong one is not a slightly worse answer; it is a hard 400. So the choice cannot be left to the caller.
  2. One retry policy instead of two. The OpenAI SDK is constructed with max_retries=0 deliberately, so the application owns retrying. Two independent retry systems multiply into behaviour nobody predicted.
  3. The error vocabulary is fixed at the boundary. Anything that goes wrong upstream arrives at tax-agent as one of a handful of named errors — UPSTREAM_TIMEOUT (504), UPSTREAM_UNAVAILABLE (503), UPSTREAM_RATE_LIMITED (429), INVALID_UPSTREAM_RESPONSE (502) — never as an SDK exception type.
  4. Tests need no API key. The gateway's 34 tests replace the provider with a fake, so CI runs with no secrets and no cost and can assert failure behaviour deterministically.
Be precise about the claim

“Nothing else talks to a model” is true for generation and not quite true overall. The embedder lives inside tax-agent: retrieval/embedders.py constructs its own AsyncOpenAI client and calls the embeddings endpoint directly, with its own key (EMBEDDING_API_KEY) and its own error type (EmbeddingFailed → HTTP 502). That is a deliberate, small inconsistency: embedding is a fast, cheap, single-shape call with no vendor dialect problems, so routing it through another hop would add latency and a failure mode for no benefit. Worth knowing, and worth being able to defend, because someone will ask.

3.4Startup: choosing implementations by name

Nothing in the request path decides which embedder or which store to use. That happens once, in lifespan, from two configuration strings:

services/tax-agent/app/main.py — lifespan, abridged

    # change. GroundedRetriever holds the policy and knows neither.
    retriever = GroundedRetriever(
        embedder=embedders.create(settings),
        store=stores.create(settings),
        settings=settings,
    )

    # Compose starts qdrant in parallel and ECS gives no ordering at all, so
    # the index may not answer on the first try. A RuntimeError is a config
    # error that retrying will never fix, so it is re-raised immediately.
    for attempt in range(5):
        try:
            await retriever.verify()
            break
        except RuntimeError:
            raise
        except Exception as exc:
            if attempt == 4:
                raise
            ...
            await asyncio.sleep(2**attempt)

Three ideas are packed into that loop and all three are worth naming.

Fail at startup, not on the first request. An unknown EMBEDDER_PROVIDER raises a ValueError listing the known names. An index whose vectors are the wrong length raises a RuntimeError that says so explicitly. Both happen before the service reports healthy, so a misconfiguration shows up as a container that will not come up — a loud, immediate, obvious failure — rather than as wrong answers in production.

Distinguish “not ready yet” from “never going to work”. Docker Compose starts Qdrant in parallel with tax-agent and ECS gives no ordering guarantee at all, so a connection failure on the first attempt is normal and retrying fixes it. A dimension mismatch is a configuration error, and retrying it five times just delays the error message. Hence the deliberately odd-looking except RuntimeError: raise before the general handler.

Ownership follows construction. The retriever is given its store, so the retriever closes its store. lifespan calls await retriever.close() and no longer knows whether there is a network connection to close at all — which is exactly right, because with VECTOR_STORE_PROVIDER=memory there is not.

Lesson

A health check is the cheapest place to put a correctness assertion. If a mismatch between two components would produce wrong output rather than an error — and an embedder/index dimension mismatch is exactly that — check it at startup and refuse to serve. Wrong answers with no exception are the most expensive kind of bug to find.

4How a question becomes an answer contents

One function, run_pipeline in app/routers/ask.py, from about 250 lines of which everything in this chapter comes. Read the diagram first, then the nine sections that walk its rows.

4.1Step one: which year, therefore which Act

Before anything is searched, the request has to decide what year it is about, because that decides which of two statutes is even eligible. Three sources, in strict precedence:

  1. An explicit tax_year in the request body wins. Source recorded as "request".
  2. Otherwise, the question text is parsed. Source "question".
  3. Otherwise None, source "none" — and None means do not filter, so both Acts stay in play.

The parsing lives in app/tax_year.py and is worth reading because it encodes the FY/AY trap from 2.5 in one subtraction:

# to 2026 as well - the single most common source of off-by-one in Indian
# tax software.
_ASSESSMENT = re.compile(
    r"\b(?:a\.?\s?y\.?|assessment\s+year)\s*:?\s*(20\d{2})", re.IGNORECASE
)
...

    if match:

The assessment-year pattern is tried first, deliberately. “AY 2027-28” also matches the bare-range pattern (20\d{2})-\d{2}, which would give 2027 — a year later, and therefore possibly a different Act. Order of attempts is load-bearing.

Which Act a year implies is reported on the stream but not used as a filter directly:

The actual exclusion happens in the store, against the tax_year_from / tax_year_to fields the corpus builder wrote onto every chunk (4.3). That is a better design than hard-coding “year ≥ 2026 means act = ITA-2025” in the query, because when a third source is added — a 2031 amendment Act, say — only the corpus builder needs to know its commencement date.

4.2Step two: the question becomes a vector

The question text goes to the embeddings endpoint and comes back as 1,536 floating-point numbers. That is the only thing the vector database can search with: it does not read words, it measures distances.

Two practical facts about this step, both measured:

  • It is a network call, and it is the entire cost of “retrieval”. Roughly 0.6 s warm; 2.7 s on a cold first request; up to 2.7 s observed. The Qdrant search that follows it takes about 13–30 ms. If someone says “retrieval is slow”, the honest answer is “the embedding call is slow, and it is somebody else's network”. Which is why the retriever times and reports the two halves separately:
retrieval/retriever.py — timed apart on purpose
        # Embedding is a network call to a third party; the store query is
        # usually local. Timed and reported apart, so a slow retrieval can
        # be blamed on the right one instead of on "retrieval".
        await report.emit("embedding", model=self.embedder.name)

        embed_started = time.perf_counter()
        vector = await self.embedder.embed(question)
        embed_ms = int((time.perf_counter() - embed_started) * 1000)
  • It must be async. The Retriever protocol says so in words, not just in types: a synchronous HTTP call here would block the whole event loop for the length of the round trip, so every concurrent request would queue behind it. One slow embed would become everyone's slow embed.

4.3Step three: the search, and the year filter

Qdrant is asked for top_k × over_fetch = 6 × 4 = 24 nearest chunks, with a filter attached. Over-fetching matters because the cap in step six throws candidates away, and you cannot refill a window from results you never asked for.

The filter is the part with a subtle bug waiting in it. An Act governs a year if it commenced on or before that year and was either never repealed or repealed after it. In the payload, “never” is stored as null. A plain range condition on a null field excludes the point, so every open-ended bound would silently vanish:

retrieval/stores.py — QdrantStore._filter
        if query.tax_year is not None:
            # An Act governs a year if it commenced on or before it and was
            # either never repealed or repealed after it. A null bound means
            # "open ended", so it must match rather than be excluded.
            def bounded(field: str, rng: models.Range) -> models.Filter:
                return models.Filter(
                    should=[
                        models.IsNullCondition(is_null=models.PayloadField(key=field)),
                        models.FieldCondition(key=field, range=rng),
                    ]
                )

            conditions.append(
                bounded("tax_year_from", models.Range(lte=query.tax_year))
            )
            conditions.append(bounded("tax_year_to", models.Range(gte=query.tax_year)))

should is Qdrant's OR; must is its AND. So the filter reads: (from is null OR from ≤ year) AND (to is null OR to ≥ year). Getting this wrong does not raise — it returns fewer results, which looks like a retrieval quality problem rather than a filter bug. The same logic is duplicated in InMemoryStore._governs and in the builder's vectorstore.year_filter, each with a comment saying it must match the others.

Lesson

When a filter can fail by returning less rather than by raising, write the intent as a sentence in a comment above it. Six months later the code reads as arbitrary and the sentence reads as a specification. Every filter in this project that touches nulls has that sentence.

4.4Step four: the score floor

Candidates scoring below retrieval_min_score = 0.30 are dropped. Qdrant always returns the k nearest chunks it has, even if the nearest thing to “what is the GST rate on restaurant services?” is some barely-related income tax provision. Without a floor, the model would always receive six passages and would always have something to work with, which is precisely how an out-of-corpus question gets answered instead of refused.

So the floor is not a quality tweak. It is the mechanism that makes the first refusal possible: if nothing clears 0.30, passages is empty and the model is never called (5.1).

4.5Step five: the named-section lookup

This is the most interesting single piece of retrieval engineering in the project, and it exists because of a measured failure (8.5): asked “what is section 139 about?”, similarity search returned 139C, 139A and 139B — and never s.139.

The reason is worth internalising. An embedding captures meaning, and a section number carries almost none. “139” and “139A” are nearly identical strings, so they embed to nearly identical vectors; nothing in the geometry prefers the exact one. A number the user typed is not a similarity problem at all. It is an exact-match problem, so it gets an exact lookup:

retrieval/sections.py
#: The cue word, then one section number or a list of them. The 1-3 digit
#: limit is load-bearing: it stops a year being read as a section, so
#: "section 139 and the 2025 Act" yields 139 alone.
_NAMED_SECTION = re.compile(
    r"\b(?:sections?|u/s|s\.)\s*"
    r"([0-9]{1,3}[A-Z]{0,4}"
    r"(?:\s*(?:,|and)\s*[0-9]{1,3}[A-Z]{0,4})*)",
    re.IGNORECASE,
)

Three decisions in that one pattern:

  • A cue word is required. “section”, “sections”, “u/s” or “s.”. A bare number in a question is far more likely to be an amount or a year than a section.
  • One to three digits. Four would match “2025”, and a query for “section 2025” would return nothing while displacing a real result.
  • Lists are handled. “80C, 80D and 80G” becomes three lookups, because a synthesis question naming three sections wants all three.

And two decisions in how the result is used, both in GroundedRetriever._exact:

retrieval/retriever.py — _exact, abridged

        Still ordered by similarity *within* those sections, so a long
        section contributes the part that answers the question rather than
        whichever chunk happens to come first.

        No score floor: the user named this section, so its relevance is
        established by the question and not by cosine distance.
        """
        try:

        except Exception as exc:
            # A failed exact lookup must not fail the request; similarity
            # search alone still produces a usable answer.
            logger.warning(...)

No score floor on the exact path. The user named the section; its relevance was established by the question, not by cosine distance. And a failure here is swallowed. The exact lookup is an enhancement over a path that already works, so if it throws, the request continues with similarity results alone and logs a warning. Degrading a feature is better than failing a request.

Exact hits are then placed before the similarity hits, so after the cap and truncation they are the ones guaranteed to survive. For SM-06 (“what is section 139 about?”) this now returns s.139 from both Acts, which is exactly the right behaviour for a deliberately ambiguous question: give the reader both and let them see the clash.

4.6Step six: the per-section cap

A section is stored as several chunks — 3,286 chunks over 1,423 sections. Nothing in a nearest-neighbour search prevents all six results from being six chunks of the same provision, and in practice that happened:

retrieval/retriever.py — the whole cap
    def _cap_per_section(self, passages: list[Passage]) -> list[Passage]:
        """Limit how much of the window any one section may occupy.

        Input order is score order and is preserved, so the best chunks of
        each section survive and the rest are dropped. Lower-ranked chunks
        of a *different* section move up into the freed slots, which is the
        point: breadth over repetition.

        The cap is 2 rather than 1 because a guidance page carries one
        section_number across many chunks; collapsing to one would throw
        away most of a page the procedural questions need.
        """
        limit = self.settings.retrieval_max_per_section
        seen: dict[tuple[str, str | None], int] = {}
        kept: list[Passage] = []

        for passage in passages:
            key = (passage.act, passage.section_number)

            if seen.get(key, 0) >= limit:
                continue

            seen[key] = seen.get(key, 0) + 1
            kept.append(passage)

        return kept

Note the key: (act, section_number), not section_number alone. s.139 of 1961 and s.139 of 2025 are different law, so they must not compete for the same two slots — which is exactly what SM-06 needs.

And note why the cap is 2 rather than 1. A guidance page such as individual-ay3 carries one section_number (the file stem) across many chunks, so capping at 1 would reduce an entire page of department guidance to a single fragment — and the procedural questions are answered almost entirely from those pages. The number 2 is a compromise between two real failure modes, not a round number.

4.7Step seven: assembling the prompt

Each surviving passage is formatted with a heading the model is expected to copy from:

app/prompt.py — format_passage
def format_passage(index: int, passage: Passage) -> str:
    if passage.section_number:

        if passage.section_title:

That else branch is the section-aware chunker's whole argument in one line. A chunk with no section number can be retrieved but never cited; the prompt says so out loud, calling it an “uncitable chunk”, so the model does not invent a reference for it. Naive fixed-size chunks (6.4) are all like that.

4.8Step eight: generation

tax-agent posts the prompt to llm-gateway over the compose network and gets back a Generation: text, model name, and four token counts including reasoning_tokens. The gateway computes that last one rather than trusting the provider to report it:

It matters because reasoning tokens are spent from the same budget as the answer. A model that thinks hard can exhaust max_tokens before it finishes writing, and the symptom is an answer that stops mid-sentence. Both services log a warning when finish_reason == "length", and the eval harness reports truncated answers as a separate line, because “the answer was cut off” and “the answer was wrong” need different fixes. On this configuration (REASONING_EFFORT=low, gpt-4.1-mini) reasoning tokens measured 0 on every sample, so it is not currently the explanation for anything — but the instrument is there for the day the model changes.

5Refusal: the design idea worth stealing contents

Most RAG systems ask the model to refuse and hope it obeys. This one makes two of its three refusals impossible to avoid, because they are decided by code that the model never sees. If you take one idea from this project into the next one, take this.

5.1Three refusals, two of them structural

The two structural refusals need no opinion from anybody:

Gate 1 — retrieve nothing and the model is never called. If no chunk clears the 0.30 score floor, the function returns before the prompt is built. There is no prompt to jailbreak, no instruction to ignore, and no token spent. The comment in the code puts it plainly:

app/routers/ask.py
    # Refusal is structural: with nothing retrieved the model is never called,
    # so it cannot be talked into answering from memory.
    if not passages:
        ...
        await report.emit(
            "refused",
            reason="nothing_retrieved",
            # The model is never called on this path, so it cannot be
            # talked into answering from memory.
            model_called=False,
        )

Gate 3 — cite nothing and the answer is discarded. If the model writes a beautiful, fluent, entirely convincing paragraph and cites none of the six provisions it was handed, that paragraph is not returned as an answer. It is returned as a refusal with refusal_reason = "not_grounded". The text is kept in the answer field — because it usually explains what the provisions do cover, which is useful — but refused is true and the citations list is empty, so no caller can mistake it for a sourced answer.

Lesson

Do not ask a language model to enforce your invariants. Arrange for the invariant to hold whatever the model does. “Refuse if you do not know” is a request; “there is no prompt because there was nothing to prompt with” is a guarantee. The general form: put the safety property in the control flow, not in the instructions.

5.2Step two: the model signals, the code decides

One refusal genuinely cannot be reached by inspecting citations, and the docstring of scope.py is the clearest statement of why:

app/scope.py — the module docstring, abridged
"""The one refusal the pipeline cannot work out for itself.

Two of the three refusal reasons are structural. Retrieve nothing and the
model is never called. Cite nothing and the answer is discarded. Neither
needs an opinion.

"You could answer this but you should not" is different. Whether a question
asks for advice - which option to choose, what is best, what someone's tax
comes to - is a judgment about meaning, and no amount of code inspecting
citations can reach it. The first baseline showed the cost: asked for the
best tax-saving mutual fund, the model correctly declined *and* cited a few
sections while explaining what the corpus does hold, so `refused = not
cited` recorded "did not refuse" on a textbook-correct refusal.

So the model signals and this module decides.
"""

The mechanism is deliberately crude, and crude is the point. Prompt rule 3 asks for one exact line as the first line of the reply:

app/scope.py
#: What the prompt asks the model to emit as its first line, one per case.
#: Deliberately phrases that cannot occur in ordinary prose about tax law.
OUT_OF_SCOPE = "REFUSE: OUT_OF_SCOPE"

Three properties make it work:

  • It cannot occur by accident. No genuine sentence about income tax contains that string.
  • It is anchored to the start. The regex begins \A, so a mid-sentence mention of the phrase is not a refusal. There is a test pinning exactly that.
  • It tolerates the decoration models add unbidden. [\s>*_#-]* before it and [\s*_:.-]* after, so **REFUSE: OUT_OF_SCOPE** or a leading bullet still matches. The model will wrap things in markdown whether you asked or not; the parser accommodates that without loosening the anchor.

And what happens to the rest of the reply matters:

app/scope.py — split_marker
def split_marker(answer: str) -> tuple[str | None, str]:
    """Separate a refusal signal from whatever followed it.

    Returns the signal name (or None) and the answer with the marker
    removed, so the model's own account of what the provisions *do* cover
    survives into the refusal instead of being thrown away.
    """

The marker is stripped and the explanation is kept. A refusal that says “I cannot tell you which regime to choose, but the provisions do cover the slab rates and the standard deduction” is far more useful than a bare decline — and a correct refusal that also tells the user what is available is exactly what the grading rubric asks for (7.6).

Why a marker rather than a second model call to classify the question? Two reasons, both recorded at the time: no extra latency, and the code still owns the decision. The model only signals; ask.py maps the signal to a reason, and cannot be talked out of a structural refusal the signal contradicts. A model that emits no marker cannot suppress gate 3; a model that emits one cannot force an answer past gate 1.

The first version of the response had refused: bool and nothing else. That single flag was being asked to mean three different things:

Lesson

When one boolean starts meaning several things, replace it with an enum and derive the boolean. Two rules keep the pair honest: the enum is the source of truth, and the boolean is computed from it in exactly one line, so the two cannot disagree. The schema comment in schemas.py says this out loud — “refused is derived from refusal_reason, never set independently” — which is the kind of comment worth writing, because it forbids a future edit.

This one change, together with three others, was worth +18 percentage points on refused_correctly — not because it changed behaviour, but because it made visible which behaviour was wrong. Five correct answers had been scoring as refusals and nothing in the summary rate said why (8.1).

5.4The conflation that is still there

The design is not finished, and the remaining flaw is worth stating plainly because it is visible in the scores.

The eval computes refused from “did it cite anything”. A model that refuses correctly while citing a nearby provision to explain what the corpus does contain therefore reads as “did not refuse”. OC-05 (“how do I register a private limited company?”) does exactly this: the prose is a textbook-correct refusal — it says the provisions do not cover company registration and explains what s.332 actually does — and because it cites s.332, the harness scores it as a failure. The hand-grading note on that row reads: third instance of that conflation.

It appeared in every one of the seven variance runs and in two of the three final runs. It is the reason refused_correctly sits at 92% rather than higher. The fix is either a declared refusal marker (tried, withdrawn, 8.11) or a scoring change that treats an explicit refusal sentence as a refusal regardless of citations — and the second is now the better bet, because the problem is in the measurement, not in the behaviour.

6The corpus pipeline contents

Two published PDFs and seven scraped web pages become 3,286 searchable, citable chunks. Every stage exists because the previous stage's output was not yet usable, and every cleanup rule in it was found by reading the text rather than guessed.

6.1Stage 1–2: PDF to clean text

Extraction is only half the job. A published Act arrives with kerning artefacts, words split across line breaks, and glyphs mapped to the wrong character. Each rule in pdf.py was found by reading the extracted text, and each is applied per page so that character offsets stay valid and a section can still be traced back to a page number for hand checking.

6.2Text to sections: one dialect per Act

The two Acts are structurally different documents, and a single parser with flags would hide that. So there is one module per Act, and the choice is a dictionary lookup:

corpus-builder/corpus/dialects/__init__.py
"""Section detection, one module per Act.

The two Acts are structurally different documents. A single parser with
flags would hide that; separate modules make each set of rules readable on
its own and let one change without risking the other.

    ITA-2025   title on the line BEFORE the number, integers 1..536
    ITA-1961   title on the SAME line, alphanumeric 80C / 80-IA / 115JD
"""

Those two lines of docstring are the entire reason the split exists. In the 2025 Act the marginal note sits on the line above the section number; in the 1961 Act it shares the number's line. No flag makes those one algorithm.

Each dialect then has its own traps, recorded as named constants:

  • 2025 — fused amendment markers. A superscript amendment marker can extract as a digit glued onto the number, so 5207. is marker 5 on section 207. The pattern allows up to five digits and then resolves against MAX_SECTION = 536.
  • 2025 — table rows that look like sections. Real sections are hundreds of lines apart; two section-shaped lines within TABLE_GAP = 4 lines of each other are table rows.
  • 2025 — titles that point back. Some titles end “[S. … of the 1961 Act]”, which is captured into maps_to_1961. It fires for only 4 of the 552 rows, which turns out to matter a great deal (13.1).
  • 1961 — body text that looks like a title. A marginal note is a phrase; lines beginning “Explanation”, “Provided”, “For the purposes”, “Notwithstanding” and so on are body, and are explicitly excluded.
  • 1961 — genuine gaps in numbering. Sections have been omitted over sixty years, so “the next number” is no guide at all. Ordering is enforced with an explicit sort key rather than by assuming sequence.
  • 1961 — schedules announce themselves by restarting at 1. There is no extractable heading. The only signal is the numbering going backwards.

Both detectors also return a list of gaps worth investigating — missing numbers for 2025, large jumps for 1961 — so the parser reports its own suspicions rather than quietly producing a short corpus.

6.3Into SQLite, and why SQLite

The stated reason is that this corpus gets interrogated constantly, and “show me every section in this chapter shorter than 200 characters” is one line of SQL and a throwaway script otherwise. It is in the standard library, it is one file, and Qdrant runs on it underneath anyway.

But the real payoff is one line of schema:

corpus-builder/corpus/storage.py — the sections table
CREATE TABLE IF NOT EXISTS sections (
    id             INTEGER PRIMARY KEY,
    act            TEXT NOT NULL,
    section_number TEXT NOT NULL,
    section_title  TEXT,
    text           TEXT NOT NULL,
    source_file    TEXT NOT NULL,
    char_start     INTEGER NOT NULL,
    char_end       INTEGER NOT NULL,
    page_start     INTEGER NOT NULL,
    page_end       INTEGER NOT NULL,
    maps_to_1961   TEXT,
    -- Catches a detector bug immediately: a duplicate fails the insert
    -- rather than silently doubling a chunk that later pollutes retrieval.
    UNIQUE (act, section_number)
);

Think about what a section-detection bug looks like without that constraint. The detector fires twice on one heading; you now have two rows for s.80C; they chunk into twice as many chunks; both sets get embedded; both sit in the index scoring nearly identically; and the top-k window fills with duplicates of one provision — which is the 8.6 failure mode, arriving by a completely different route and looking identical from the outside.

With the constraint, the same bug is an IntegrityError during parsing, on the line that caused it, minutes after you wrote it.

Lesson

Put a uniqueness constraint wherever your pipeline has an implicit “there is exactly one of these” assumption. It converts a silent quality degradation five stages downstream into a loud crash at the source. This is the single highest-leverage line in the corpus builder, and it is free.

Two more properties of storage.write are worth noting. It is scoped by act — DELETE FROM sections WHERE act = ? before inserting — so re-parsing the 2025 Act does not wipe the 1961 rows. And it is therefore idempotent: while you are tuning detection rules you can re-run the parser as often as you like without accumulating garbage. Both make experimentation cheap, which is what makes it happen.

6.6The guidance pages, labelled apart

Seven text files scraped from the Income Tax Department's site sit in data/raw/guidance/: three individual pages, two company pages, an individual-business page, and a do's-and-don'ts page. They are not statute, and the module says so in its first line:

corpus-builder/corpus/guidance.py
"""Chunk Income Tax Department guidance pages.

These are not statute. The department publishes them to explain which return
applies, what the slabs are, and which deductions exist - in the vocabulary
people actually use. They are indexed under a separate act label so an answer
can never present guidance as law.

Every page carries the department's own disclaimer, and it is repeated on
every chunk rather than kept once at the top: a passage retrieved from the
middle of a page must still say what it is.
"""

Three defences keep guidance from being quoted as law:

  1. A separate act code, DEPT-GUIDANCE, which is what appears in every citation from these pages.
  2. A disclaimer inside every chunk's own text, not just in metadata: each chunk ends “(Departmental guidance, not statute. Source: …)”. Metadata can be dropped by a later refactor; text travels with the passage into the prompt.
  3. The page title and section heading on every chunk, so a citation names something a reader can actually find on the page.

Two parsing subtleties are worth studying because both are places where a reasonable-looking rule destroys the most valuable data on the page.

The assessment-year conversion, again. These pages say “AY 2026-27”. The income year that assesses is FY 2025-26, so the tax_year is 2025 — and getting it backwards would file every page under the wrong Act. The function that does it is four lines with a three-line docstring explaining the subtraction.

The slab-table trap. Chunks break at headings, and a heading is detected by being short and not ending like prose. A slab table row — ₹ 8,00,000 - ₹ 12,00,000  10% — is short and unpunctuated, so a naive length test calls it a heading and discards it. The rates are the single most valuable thing on these pages. The fix is explicit:

guidance.py — is_heading

    Slab tables are the trap here: "₹ 8,00,000 - ₹ 12,00,000  10%" is short
    and unpunctuated, so a naive length test calls it a heading and discards
    the rates - which are the single most valuable thing on these pages.

“A heading is a phrase; a row of figures is data” is the whole rule, and the three tests implement it: no rupee sign, no percent sign, and no more than 35% digits.

6.7Reproducibility: the manifest

An answer about tax law is only meaningful relative to a version of the law. So the corpus records where it came from:

  • data/manifest.json holds the source URL and a hash for everything in data/raw/. It is the one file under data/ that is not gitignored.
  • make manifest records them; make manifest-check re-downloads the sources and detects whether the law has been republished underneath you.
  • Every Qdrant point carries a corpus_date stamped at upload time, and every answer returns a corpus_date taken from the retrieved passages rather than from the running process:
app/routers/ask.py — _corpus_date
def _corpus_date(passages: list[Passage], settings: Settings) -> str:
    # The date belongs to the data that was retrieved, not to this process,
    # so it stays true even if the service outlives the index that built it.
    for passage in passages:
        if passage.corpus_date and passage.corpus_date != "unknown":
            return passage.corpus_date

    return settings.corpus_date

That is a small thing with a large implication: a container that has been running for a month, against an index that was rebuilt last week, reports last week's date. The alternative — a date baked into configuration at deploy time — would eventually lie.

This is the heart of the project. Everything else is engineering that could be judged by reading it; this is the part that decides whether the engineering worked. Give it the most time.

7.1Why an eval at all

The argument is in the first paragraph of eval/PLAN.md and it is better than any general case for testing:

From eval/PLAN.md

Turn “the retrieval is good” into a number, and keep it a number as the system changes. Four bugs found on 2026-09-14 — collapsing chunks, dropped slab tables, unrecognised citations, truncated answers — all failed by producing less, silently. None would fail a smoke test. Only a score across many questions catches that class of defect.

That phrase — producing less, silently — is the thing to hold on to. A RAG system's characteristic failure is not a crash and not gibberish. It is a fluent, well-cited, plausible answer that quietly omits a third of the law. It passes every unit test. It passes a manual spot check, because the part it did answer is correct. The only instrument that detects it is a set of questions whose complete correct answers you already know.

Consider SY-03: “how is income from house property computed and what deductions apply, under the 1961 Act?”. The answer correctly explained s.22 (the charge) and s.24 (the deductions) and did not mention s.23 (annual value, how determined), because two chunks of s.24 had crowded s.23 out of the window. Nothing about that answer looks wrong. You only know it is incomplete if you wrote down in advance that a complete answer needs 22, 23 and 24.

7.4Why a signal that does not apply stays None

Three states, not two: True, False, None. None means “this question cannot be scored on this signal”, and it is excluded from the denominator entirely:

eval/run.py
def rate(results: list[Result], attribute: str) -> tuple[int, int]:
    """Passes and applicable count for one signal."""
    applicable = [getattr(r, attribute) for r in results]
    applicable = [v for v in applicable if v is not None]

    return sum(1 for v in applicable if v), len(applicable)

And the scoring function returns early for questions that must refuse:

eval/run.py — score(), abridged
    should_refuse = bool(question.get("should_refuse"))
    result.refused_correctly = result.refused == should_refuse

    if should_refuse:
        # Nothing else is meaningful: a correct refusal cites nothing.
        return result

Consider the two alternatives you might reach for instead, and what each does to the number:

  • Count non-applicable as a pass. The five out-of-corpus questions would each score grounded = True for citing nothing, which is backwards, and grounded would read 31/40 = 78% instead of 26/35 = 74%. The rate goes up and means less.
  • Count non-applicable as a fail. Correct refusals would drag down retrieval_hit, so improving refusal behaviour would worsen your retrieval number. The metric would actively punish correct work.

This is why the denominators in the scoreboard are all different: 28 for retrieval_hit (only 28 questions name an expected section), 33 for act_correct, 35 for grounded, 40 for refused_correctly and no_fabrication. When you read “26/28”, the 28 is doing real work.

Lesson

A three-valued signal — pass, fail, not applicable — is almost always the right shape for an eval. Two-valued metrics force you to lie about the cases that do not fit, and the lie always flatters you. If your rates all share one denominator, check whether they should.

7.5Why answer_correct is graded by hand

The reason given in the harness docstring is one sentence and it is sufficient: an LLM judge has its own error rate, and you would end up measuring the judge.

Unpack that. Suppose you use a model to grade the answers. Now your score is the composition of two uncertain processes, and when it moves you cannot tell which one moved. Worse, both processes share failure modes — a judge asked whether an answer is supported by a provision is doing the same reading-comprehension task that produced the answer, with the same blind spots. The errors are correlated, which is the worst possible property in a measurement instrument.

So the split is deliberate: retrieval accuracy carries most of the signal and is fully objective, so the harness runs unattended; answer correctness is a human pass over 40 rows, done once per meaningful configuration rather than once per run.

eval/grade.py is built around making that pass survivable:

  • It walks only the ungraded rows, so it is resumable.
  • It shows the question, the expectations from the YAML (including the note), what came back, the auto-scored signals, and the full answer wrapped to 78 columns.
  • It takes y / n / s (skip) / q (save and quit), and an optional free-text note.
  • It saves after every verdict, via a temp file and an atomic rename, so a crash or a closed terminal loses nothing.
  • It refuses to grade rows that errored, because a verdict on an errored row records an opinion about the harness rather than about the system.

Those grader notes turned out to be the most valuable artefact in the whole eval directory. They are what this book's error chapter is largely built from. Two examples, verbatim from eval/runs/tier0.csv:

7.6The rubric: judge against the corpus, never the world

This is the part that matters, and it is a discipline rather than a procedure:

The rubric, from eval/grade.py

Groundedness and correctness relative to the corpus — not whether the answer matches Indian tax law as you know it. An answer that is true in the world but unsupported by the cited provision is a failure of this system, and an answer that faithfully reports a provision is a pass even if the corpus itself is out of date. Grading against your own knowledge instead makes the score unreproducible, which defeats the point of having one.

Two graded rows show exactly what this costs and why it is still right.

EF-03 — passed

“What deduction is available for rent paid by a self-employed person under the 1961 Act?” The answer reported s.80GG as the corpus prints it: two thousand rupees per month or twenty-five per cent. The real-world limit has been ₹5,000 per month since 2016. Grader's note: “faithful … grading against current law would wrongly fail this”. Pass.

YS-01 — passed

“Which deduction applies to life insurance premium for FY 2024-25?” The answer said ₹1,00,000, because corpus s.80C reads “does not exceed one lakh rupees” — pre-2014 text. The real limit is ₹1,50,000. Grader's note: “corpus wins”. Pass.

Both of those are, in the real world, wrong answers. Marking them as passes feels wrong and is correct, for a reason worth being able to articulate: this system's job is faithfulness to its sources, and the score has to measure that one thing. The staleness of the corpus is a separate problem with a separate fix (re-scrape, re-parse, re-index — and make manifest-check exists precisely to detect it), and it has a separate reporting channel: corpus_date on every answer. Blending the two into one number would mean that re-scraping the corpus and improving the retriever both move the same digit, and you would never know which you had done.

Three more rules in the rubric round it out:

  • Do not fail an answer for citing too little. Retrieval is scored separately. Judge what the answer did with what it had. Hence SY-03's note: “missed s.23 but that is retrieval, not the answer” — and retrieval_hit already counted that miss, so counting it twice would double-penalise one defect.
  • A partial answer that names its gap passes; a silent omission fails. That is prompt rule 4, scored. SY-05 passed for saying plainly that health insurance was not supplied.
  • For a should-refuse question, judge the refusal. Did it decline for the right reason and say what it could not cover, rather than declining something the corpus actually answers?

7.7Running it and grading it

Try it

make grade-summary CSV=… — rates only, changing nothing.

Two things the harness does that are easy to overlook and both matter.

It paces itself and retries the right statuses. Three seconds between questions by default, and up to four retries on 429, 503 or 504 — all statuses that mean the question was never answered. The reasoning is explicit in the docstring: recording a rate-limited question as a result would score the quota rather than the system, and a run with holes in it cannot be compared against the next one. It prefers the server's own Retry-After header when there is one, capped at 60 seconds so one unlucky question cannot stall a whole run.

It reports how much retrying it had to do.

eval/run.py — summarise()
    retried = [r for r in results if r.retries]

A run that needed fifteen retries is not comparable with one that needed none, and the line at the bottom of the summary tells you which kind you are looking at before you draw a conclusion from it.

What we saw
The baseline run scored refused_correctly at 29/40, and five of the failures were questions the system had answered correctly. PR-02 (“who cannot file ITR-1 Sahaj?”) listed exactly the right categories of taxpayer — and was recorded as a refusal.
What was actually wrong
The corpus used three act codes: ITA-1961, ITA-2025 and ITD-GUIDANCE (ITD = Income Tax Department). The guidance prefix differed from the statute prefix by one letter, and gpt-4.1-mini reliably wrote ITA-GUIDANCE. split_citations then rejected it — correctly, since that (act, section) pair was never supplied — so the answer cited nothing, and refused = not cited recorded a refusal on a perfectly good answer.
How we found it
The tax-agent log. Six of the seven unsupported-citation warnings in the baseline run were this one substitution:
refs=['ITA-GUIDANCE s.individual-ay1', 'ITA-GUIDANCE s.company-ay1', ...]
The warning was already there because unsupported_citations is logged and returned. Nothing in the summary rate said why, which is what the refusal_reason field later fixed.
The fix
Rename the label to DEPT-GUIDANCE in corpus-builder/corpus/guidance.py and reindex. It shares no prefix with ITA-, and still contains the hyphen the citation regex requires. Because point_id includes the act code, the old ITD- points had different IDs and had to be deleted by hand rather than being overwritten — a latent trap for any future payload change that alters the ID.

The alternative fix — listing the valid act codes in the prompt — was considered and judged weaker, for a reason worth remembering: the model already sees the correct code in the provision heading, right there in the same prompt, and still substitutes. Adding a sentence telling it to do what it can already see does not address the cause.

Lesson

Identifiers that a language model has to reproduce exactly should be designed to be hard to confuse, exactly as you would design them for a human typing them. One-letter differences between semantically adjacent labels are a bug waiting in your data model, not a discipline problem in your prompt. Fix it at the source and the failure mode disappears; fix it in the prompt and you are negotiating.

8.2Bracket citations: [1], [2]

Error
What we saw
An answer to PR-02 containing twelve references of the form [1], [2] … and no real citations at all. Scored as ungrounded.
What was actually wrong
The prompt numbers the supplied provisions [1] to [6] so they read as a list. The model took those numbers to be the citation format — which is a completely reasonable reading of the input it was given. Those numbers mean nothing to a reader of the answer: they index a list the reader never sees.
How we found it
grounded was 74% at baseline and the failing answers were visibly full of brackets in the CSV's answer column.
The fix
Prompt rule 1 gained three worked citation examples — one per act code, including a guidance one — plus an explicit ban: “Never write a bracketed passage number such as [1] or [2] — those number the list below and mean nothing to the reader.”
Lesson

Anything you put in a prompt is a thing the model may imitate, including your own formatting scaffolding. If you number a list for readability, expect the numbers to come back at you, and either say not to use them or do not number the list. Worked examples beat prohibitions, and having both beats either — note that the fix here is one example per act code, not merely a rule.

8.3Fabricated sources

Error
What we saw
Answers citing provisions that do not exist: DEPT-GUIDANCE s.individual-ay6 and s.individual-ay5 (only ay1 to ay3 exist), s.company-ay3 (only ay1 and ay2), ITA-1961 s.115BAC (not in the corpus at all), and ITA-2025 s.80D (80D is a 1961 section; the 2025 equivalent is 126).
What was actually wrong
Nothing in the code. The model was pattern-completing: having seen individual-ay1, individual-ay2 and individual-ay3, inventing ay6 is an extrapolation, and 115BAC is real-world knowledge leaking past the instruction to use only what was supplied.
How we found it
Three ways, which is why it is well understood. The service already logged unsupported citations as warnings. Then unsupported_citations was added to the response so the harness could count it as the no_fabrication signal. Then hand grading named the specific inventions in the notes.
The fix
Prompt rule 2 gained one clause: “never cite a section number that does not appear in a heading below, even if you know it exists”. That clause took fabrications from 3 to 1 in a run. Structurally, fabricated references were already harmless to the caller — they are stripped out of citations — so this was about quality, not safety.

This is the most dangerous failure the system can have, and the schema comment says why in one sentence: a fabricated section reference looks exactly like a correct one. It is not detectable by reading the answer. It is only detectable by comparing against what was supplied, which is a mechanical check — so it should be done mechanically, every time, and reported as a number.

Lesson

The fabrications did not go to zero and will not. Design for that: strip them at the boundary, count them in the response, and score the count. A failure mode you have quantified and contained is a managed risk; the same failure mode with a prompt rule and no counter is a hope. PR-06 still fabricates on every run (13.2) — and the system is safe anyway, because the containment is structural.

8.4The company guidance scrape that lost ITR-6

Error
What we saw
PR-06, “which return form applies to a company?”, failing persistently. Retrieval was finding the right pages. The answer was honest — it said the form number was not in what it had — and then invented a page to cite anyway.
What was actually wrong
data/raw/guidance/company-ay1.txt and company-ay2.txt had lost their ITR form labels during scraping. The individual pages kept theirs (“ITR-1 (SAHAJ) – Applicable only for Individual”), but the company pages have only the bare descriptions (“Applicable for Companies other than those claiming exemption u/s 11…”) with no “ITR-6” or “ITR-7” heading. Almost certainly the accordion widget's heading text, which the scrape did not capture.
How we found it
grep ITR data/raw/guidance/company-ay1.txt finds only incidental prose mentions. One command.
The fix
Not yet applied. Re-scrape the two company pages preserving the accordion and heading labels, then make index-guidance. Until then, PR-06's failure is a corpus bug, not a retrieval bug, and is documented as such so nobody spends a day tuning the retriever over it.
Lesson

A question with unattainable ground truth scores the corpus, not the retriever, and quietly depresses a whole category. When a question fails repeatedly, the first thing to check is not the retriever but whether the answer is in the corpus at all — and grep over data/raw/ is faster than any amount of thinking. Keeping the raw sources on disk, readable, is what makes that check a ten-second job.

8.5Section 139, which could not be found

Error
What we saw
“What is section 139 about?” returned 139C, 272B, 139A and 139B — never s.139, from either Act. “Section 80C … corresponds to which section of the 2025 Act?” returned 80B, 80GGA, 80CCA and 80CCE — never 80C, never 123.
What was actually wrong
Embeddings encode meaning, and a section number carries almost no meaning. “139” and “139A” are nearly the same string, so they are nearly the same vector, and nothing in the geometry prefers the exact match. Description-worded queries worked fine throughout — 234A and 423 were both retrieved happily from “which section charges interest for a late filed return”. It was specifically numbers that failed.
How we found it
Probing the /search endpoint by hand on 2026-09-14. /search exists precisely for this: retrieval only, no model call, no cost, so you can interrogate the index freely. The probe predicted that SM-01 and SM-06 would fail before the eval had ever been run on them, and they did.
The fix
named_sections() plus a Qdrant payload filter on section_number — the exact-lookup path of 4.5. SM-06 had failed every previous run and now returns s.139 from both Acts.
Lesson

Vector search is a tool for “find me something like this”, and some questions are not like that. An identifier the user typed — a section number, an invoice number, an error code, a SKU — is an exact-match problem and should get an exact-match query. This is what “hybrid search” means in practice, and you do not need a library for it: you need a regex that spots the identifier and a payload filter that fetches it. Also: build a retrieval-only endpoint early. Being able to probe retrieval without paying for generation changes how often you actually look.

8.6One section flooding the window

Error
What we saw
On one query, four of the six prompt slots were four different chunks of s.234A. On SY-03, two chunks of s.24 crowded out s.23 (“Annual value how determined”) completely, so an answer about house property silently lost a third of the law.
What was actually wrong
A section is many chunks, and nothing in a nearest-neighbour search stops all the near neighbours being pieces of one provision. Worse, it also pushes 2025-Act counterparts to the bottom, which hurts precisely the section-mapping questions.
How we found it
/search probing again, on the same afternoon as 8.5, and then the eval: synthesis questions need several distinct provisions, so this shows up as a category-level weakness rather than a single failing question.
The fix
retrieval_max_per_section = 2 with a 4× over-fetch (4.6). Not 1, because a guidance page carries one section number across many chunks.

The more sophisticated fix would have been MMR or a dedup-by-section pass with a similarity matrix. The cap is 15 lines, has no tuning surface beyond one integer, and was measurable within one afternoon.

Lesson

Diversity in a retrieved set is a separate requirement from relevance, and ranking by score alone optimises only the second. Before reaching for MMR or a reranker, ask whether a hard cap on the obvious grouping key gets most of the benefit — it usually does, and it is far easier to explain, test and reason about. Measure the cheap version first; only then find out whether the clever version is worth building.

8.7₹150000 against ₹1,50,000

Error
What we saw
EF-01 failing contains_expected despite a completely correct answer. The question asks for the maximum deduction for life insurance premium under the 2025 Act; the expectation was the literal string "150000".
What was actually wrong
The corpus prints the same figure two different ways. Corpus s.123 reads “does not exceed ₹150000” with no thousands separators; the department's guidance writes “₹1,25,000” with Indian-style separators. Prompt rule 5 requires figures quoted exactly, so both forms are faithful, and models reformat freely between them. A literal substring test was measuring formatting luck.
How we found it
Hand grading. The note on EF-01 reads: “correct: corpus s.123 prints ₹150000 without commas, so this quoted it exactly (rule 5). answer_contains expectation is the thing that is wrong”.
The fix
Normalise digit separators on both sides before comparing — and only separators that sit between two digits, so nothing else in the text is touched:
eval/run.py
def _normalise_digits(text: str) -> str:
    """Drop separators that sit between two digits, and nothing else."""
    return re.sub(r"(?<=\d)[,\s](?=\d)", "", text)

The lookbehind and lookahead are what make this safe. A blanket replace(",", "") would also join “insurance, health” into “insurancehealth” and break every other phrase expectation in the file.

Lesson

Assertions on generated text must be as loose as the space of correct answers and no looser. A brittle expectation does not merely produce a false failure — it produces a false failure you will eventually “fix” by changing the system, which is how a working system gets broken in pursuit of a metric. Normalise what does not matter (separators, case, whitespace); never normalise what does.

8.8The expectation that rewarded bad behaviour

Error
What we saw
PR-05 (“is the new tax regime the default, and can a taxpayer opt out?”) scoring as a failure while giving a substantively correct, fully grounded answer. PR-04 scoring better while citing a provision it was never given.
What was actually wrong
PR-05's expectation was answer_contains: ["115BAC"]. That section is not in the corpus. So the only way to satisfy the expectation was to cite a provision the model had never been supplied — that is, to fabricate. PR-04 did exactly that and was rewarded; PR-05 stayed grounded and was marked down for it.
How we found it
Hand grading, and the two notes read as a matched pair. PR-04: “cites ITA-1961 s.115BAC, which is NOT in the corpus — an ungrounded citation from model knowledge, violating rule 2”. PR-05: “it did NOT cite 115BAC — correctly, since that section is absent from the corpus. the answer_contains expectation rewards the opposite”.
The fix
The expectation was deleted, with the reason recorded in the YAML itself so nobody re-adds it.
eval/questions.yaml — PR-05
    # Was ["115BAC"], which actively rewarded bad behaviour: that section
    # is NOT in the corpus, so the only way to satisfy it was to cite a
    # provision the model was never given. PR-04 did exactly that and PR-05,
    # which stayed grounded, was marked down for it.

This was not the only bad expectation. Tier 0 widened three over-narrow ones (SM-03 and SM-05, which name a 1961 section in the question and were failing act_correct for citing it), and Tier 1 widened SY-06's expected_sections to ["80C", "123"] because with tax_year: null the 2025 equivalent answers the life-insurance half just as well. Four of the forty questions had ground truth that punished correct behaviour.

Lesson

Ground truth is code and has bugs. Review it as code: when a question fails, form the hypothesis “the expectation is wrong” alongside “the system is wrong”, and check it first because it is cheaper. Most importantly: an expectation that can only be satisfied by behaviour you are trying to prevent is worse than no expectation at all, because chasing it makes the system worse while the number goes up. Write the reason for a deleted expectation into the file.

8.9The 30-second gateway timeout

Error
What we saw
Roughly a third of calls failing with UPSTREAM_TIMEOUT and HTTP 504.
What was actually wrong
The gateway's timeout was the 30-second default, and the model was taking 6–21 seconds for these prompts. Perfectly good requests were being cut off by our own patience.
How we found it
The error rate and the error code. UPSTREAM_TIMEOUT names its own cause, which is the payoff of having a specific error vocabulary rather than a generic 500.
The fix
Not just “raise it to 60” — that would have collided with the tax-agent's own 60-second budget, so a slow model would surface as a race between two layers rather than as a clean timeout from the one that actually waited. The whole ladder was set instead: model 60 < gateway 75 < harness 90 (12.6), in the docker-compose.yml environment blocks rather than in the services' .env files, so the relationship between the three is visible in one place.

There is a second decision hiding in this fix, and it is the more interesting one. The gateway deliberately does not retry timeouts. Its retry loop catches only (UpstreamRateLimited, UpstreamUnavailable):

llm-gateway/app/services/openai_compatible.py — generate()
        for attempt in range(self.settings.max_retries + 1):
            try:
                return await self._generate_once(prompt=prompt, max_tokens=max_tokens)

            except (UpstreamRateLimited, UpstreamUnavailable) as exc:

With a 60-second upstream timeout, one attempt already consumes the entire max_retry_time_seconds: 60 budget, so a gateway-level retry of a timeout would be skipped anyway — and if it were not skipped, it would blow through the gateway's own 75-second ceiling and break the ladder. The harness retries 504 instead, one layer out, where there is time for it.

Lesson

Timeouts and retries are one design, not two features. Every retry multiplies the worst-case duration of the layer it lives in, so a retry policy that ignores the enclosing timeout is a policy that will be silently skipped or will break its container. Write the ladder down — the numbers and the reason for their order — next to where they are configured. docker-compose.yml in this project carries that comment, and it is the only place all three numbers appear together.

8.10Quota exhaustion, HTTP 429

Error
What we saw
OC-05 erroring with HTTP 429 in the first out-of-corpus run, leaving a hole in the results. In the same session, requests that normally took 5–8 seconds were taking 21.
What was actually wrong
Quota exhaustion — and the two symptoms were probably one cause. The slowdown to ~21 s appeared in the same session that then hit a hard GATEWAY_RATE_LIMITED, so throttling appears to show up first as latency and only later as a refusal. Treating 20 s as the model's normal speed would have been the wrong conclusion.
How we found it
The harness reported the errored row rather than scoring it, and the latency profile was measured from logs across four complete requests.
The fix
Two layers. The gateway raises UpstreamRateLimited carrying the provider's Retry-After when there is one, and tax-agent forwards it as a Retry-After response header on its 429. The harness then retries 429, 503 and 504, preferring that header over its own guess, capped at 60 s, and counts the retries so a quota-bound run can be identified as such.

One more piece of this belongs here because it cost real confusion: a ChatGPT Plus or Pro subscription grants no API access. API billing is separate and prepaid. That was the initial assumption and it was wrong. The project currently runs on openai / gpt-4.1-mini, whose free daily bucket (2.5M tokens for mini models) comfortably covers an eval run at about 120K tokens — which is why the variance chapter can say “tokens are free, so there is no reason to compare single runs”.

Lesson

Rate limiting is not only an error; it is a performance profile. Before concluding that a provider is slow, check whether you are being throttled — and re-measure after a quota reset before writing a number down. And never record a rate-limited request as a result: a run with holes in it cannot be compared with the next one, which is the whole reason the harness retries rather than scoring the failure.

8.11The second marker that was withdrawn

Error
What we saw
A change intended to fix OC-05 made SY-01 and YS-07 worse, and every attempt to reorder the precedence broke something else.
What was actually wrong
A companion marker, REFUSE: NOT_IN_CORPUS, was added to prompt rule 2 so the model could declare “I read these and they do not cover it” rather than have it inferred from an absent citation. But rules 2 and 4 conflict: the model emitted the marker on questions it could answer in part, refusing wholesale where rule 4 wanted a partial answer. SY-01 found s.80C for life insurance, lacked health insurance and rent, and declined all three.
How we found it
Four eval runs, and the realisation that neither precedence order worked. Marker-wins broke SY-01 and YS-07; citations-win broke OC-01 and OC-05. Neither order is right for both cases, because the real problem was the model emitting the marker when it should not.
The fix
Withdraw the marker. Keep the infrastructure: not_in_corpus stays in RefusalReason, and the two-marker split_marker in scope.py stays with its tests. The prompt simply does not ask for it. The code carries a long comment explaining the attempt so it is not repeated blindly.

The real error was procedural, and it is the one worth learning. Two changes were bundled into rule 2 at once: the marker, and the anti-fabrication clause of 8.3. The clause took fabrications from 3 to 1 and was worth keeping. The marker was a wash. Bundled together they looked like a mixed result, and separating them is what produced the best configuration. Four runs were spent disentangling two edits.

Lesson

One change per eval run. Not as a matter of tidiness — as a matter of arithmetic. With two changes and one number you have two unknowns and one equation, and the temptation is to keep or discard both together, which loses a good change to a bad one. When an attempt fails, write down what was tried and why it lost, next to the code that would be touched if you tried again; otherwise the same idea comes back in three months looking fresh.

8.12“ITA-2025 section 124”

Error
What we saw
SM-04 scoring as a refusal on run after run, while its answer was correct. The failure was stable, which made it look like a real defect rather than noise.
What was actually wrong
The answer said “covered under ITA-2025 section 124”. The prompt asks for the s.124 form, and the citation regex accepted only that form. So the parser saw no citations, gate 3 fired, and a correct grounded answer was converted into a refusal. The parser was manufacturing ungrounded answers out of correct ones.
How we found it
Reading the answer column of the CSV for a question that failed consistently. Consistency was the clue: noise flickers, defects persist (9).
The fix
Widen the regex to accept both forms, with the reason recorded above it:
app/prompt.py
#: "s.124" is asked for, but "section 124" identifies the same supplied
#: provision just as unambiguously, and rejecting it turns a correct answer
#: into an ungrounded one.
_CITATION = re.compile(
    r"\b([A-Z][A-Z0-9]{1,5}-[A-Z0-9]{2,10})\s+"
    r"(?:s\.\s*|sections?\s+)"
    r"([0-9A-Za-z][0-9A-Za-z\-]*)"
)

That was one of the three Tier 1 changes that took retrieval_hit from 83% to a stable 93%. Note what it implies: part of the apparent retrieval improvement was not retrieval at all. It was the measurement instrument starting to recognise citations it had been discarding — because retrieval_hit is computed from citations the model writes, so a citation parser bug reads as a retrieval failure.

Lesson

A parser that validates model output is part of the system's correctness, not a detail. Make it accept every unambiguous form of the thing you asked for, and be strict only where strictness prevents a real error. The test is simple: would a human reader consider this reference identified? If yes, and it points at something you actually supplied, accept it. Rejecting valid output is indistinguishable, from the outside, from the model having failed — and you will debug the model instead of the regex.

8.13The viewer that truncated at 300 characters

Error
What we saw
Answers appearing to stop mid-sentence in make ask-stream output — which is exactly what a finish_reason: length truncation looks like, and truncation was a known real failure mode in this project.
What was actually wrong
Nothing in the service. eval/watch.py, the little script that renders the event stream readably, sliced the answer to 300 characters before printing it.
How we found it
Comparing against the JSON from make ask, which showed the complete answer.
The fix
Print the whole thing, wrapped to the terminal width with paragraph breaks preserved, and leave a comment saying why:
eval/watch.py
            # Printed in full and wrapped. An earlier version sliced this to
            # 300 characters, which read exactly like a truncated answer -
            # the opposite of what a viewer is for.
Lesson

Your debugging tools are part of your system and can lie to you. A viewer whose display looks like a real failure mode is worse than no viewer, because it costs you an investigation of the wrong component. When a tool abbreviates, make the abbreviation visible — an ellipsis, a “truncated to N of M” line — or do not abbreviate. And when a symptom looks familiar, confirm it in a second place before you start fixing.

8.14Two from the corpus: dropped slabs, truncated answers

eval/PLAN.md names four bugs found on 2026-09-14 that together motivated the eval: collapsing chunks, dropped slab tables, unrecognised citations, truncated answers. Two of those have their own sections above — unrecognised citations is 8.12, and the chunk problems are 8.6 and the UNIQUE constraint of 6.3. The other two are worth recording briefly.

Error — dropped slab tables

What we saw: the tax slab rates missing from the indexed guidance, so PR-04 (“what are the slab rates?”) had nothing to work from. What was wrong: the guidance chunker splits at headings, and a heading was detected as “short line that does not end like prose”. A slab row — ₹ 8,00,000 - ₹ 12,00,000  10% — is short and unpunctuated, so it was classified as a heading and discarded along with its rates. The fix: is_heading now rejects any line containing a rupee sign or a percent sign, or more than 35% digits. “A heading is a phrase; a row of figures is data.”

Error — truncated answers

What we saw: answers ending mid-sentence, genuinely this time. What was wrong: max_tokens is a ceiling on the model's whole output budget, and on a reasoning-capable model part of that budget is spent thinking before any visible text appears. A model that thinks hard can run out of room to write. The fix: keep reasoning_tokens as a separate reported number (computed as total − prompt − completion), warn on finish_reason == "length" in both services, and list truncated question IDs as their own line in the eval summary. On the current configuration reasoning tokens measure 0 — but the instrument stays, because the next model may be different.

Lesson

Both of these are the same bug wearing different clothes: a rule that was right for the common case silently destroyed the most valuable minority case. A heading detector that is right about headings and wrong about rate tables loses the rates. A token budget that is right about prose and wrong about reasoning loses the end of the answer. When you write a classifier — and a length heuristic is a classifier — go looking for the class of input where being wrong is most expensive, and test that one specifically.

8.15Gemini’s empty answer: one flag doing two jobs

Error
What we saw
Testing the gateway image before pushing it to ECR, the Gemini vendor returned INVALID_UPSTREAM_RESPONSE — “LLM returned no message content”. Not a 400. The request was accepted and came back empty.
What was actually wrong
Two separate facts had been collapsed into one flag. Gemini accepts reasoning_effort on every model, so vendors.py marked every Gemini model as a reasoning model — and reasoning models were also given max_completion_tokens instead of max_tokens. But max_completion_tokens covers thinking and writing. With a ceiling of 20 and 79 reasoning tokens, the model spent the entire allowance thinking and had nothing left to write the answer with.
How we found it
By exercising the built image against both vendors before pushing, rather than pushing and trusting it. The previous production image had sent Gemini max_tokens successfully for four days, so the failure was a regression introduced by the refactor.
The fix
Separate the two questions — does this model accept reasoning_effort? and does it need max_completion_tokens? — into independent fields:
services/llm-gateway/app/vendors.py
# Whether a reasoning model also needs max_completion_tokens in place of
# max_tokens. True for OpenAI, where reasoning models reject max_tokens
# outright. False for Gemini, which accepts reasoning_effort on every
# model but has served max_tokens in production for days.
reasoning_needs_completion_tokens: bool = True

Retested at max_tokens=20: both vendors answered correctly, Gemini with 15 reasoning tokens comfortably inside the budget.

Lesson

When two facts happen to coincide for the case in front of you, resist storing them as one. “Accepts a thinking budget” and “needs a different parameter name” were true together for OpenAI and false together for nothing — until Gemini, where the first was true and the second was not. A boolean that means two things is the same bug as refused meaning three things (5), just smaller.

Note also how it failed: HTTP 200, a well-formed response, no content. A hard 400 would have been kinder. Silent emptiness is the failure mode to fear, and the only defence is exercising the real artefact before shipping it.

8.16The push target that pushed the wrong service

Error
What we saw
Nothing yet — this one was caught by reading, before it could fire. Worth recording because of what it would have cost.
What was actually wrong
make ecr-push hardcoded $(AGENT), the tax-agent. But the deployed ECS task runs the llm-gateway on port 8000. Running that target would have built a tax-agent image — listening on 8080 and requiring QDRANT_URL — and pushed it into the repository the gateway task pulls from. The task would have pulled it, failed to start, and failed its health check, with nothing in the error to suggest the image was simply the wrong program.

Makefile

Lesson

A deploy command that cannot say what it deploys is a loaded gun. Restructuring the repository silently repointed this one, because nothing tied the Makefile's idea of the service to the task definition's. The general rule: after you move files, re-read every script that names a path. The compiler checks imports; nothing checks a string in a build command.

9Measurement discipline contents

The most important lesson in the project, and the one that generalises furthest beyond it. Four configurations were compared on single runs, and every conclusion drawn from those comparisons was inside the noise — including two “regressions” that were nothing of the kind.

9.1Seven runs of almost the same thing

Two facts made the trap especially easy to fall into.

First, two early runs came back byte-identical, which made the harness look deterministic. It is not. The retrieval half is deterministic — same question, same vector, same index, same six passages — but retrieval_hit is computed from the citations the model writes, and the model is sampled. So a signal that sounds like a property of the retriever is in fact a property of the retriever and the model together, and the second one wobbles.

Second, the effect sizes being chased were genuinely small. Forty questions means one question is 2.5 percentage points, and a signal with a denominator of 28 moves 3.6 points per question. A change that fixes one question produces a delta indistinguishable from doing nothing.

9.2eval/compare.py

So a tool was written whose only job is to refuse to let you fool yourself. It reads several CSVs, reports each signal's mean and its range, and — given two groups — marks a difference REAL only when the two ranges do not overlap:

eval/compare.py — the verdict
            before, after = left[column], right[column]
            change = statistics.mean(after) - statistics.mean(before)

            # Overlapping ranges mean the runs cannot tell the two apart.
            overlap = min(before) <= max(after) and min(after) <= max(before)
            verdict = "within noise" if overlap else "REAL"

That is not a statistical test, and it does not pretend to be. It is a blunt rule that is correct about the thing that matters: if the worst run of the new configuration is worse than the best run of the old one, you have not demonstrated anything. Three runs is far too few for a confidence interval; it is exactly enough for “do these two sets of numbers even separate?”. Picking the honest crude test over the impressive-looking one is the right call when you have three samples.

It also reports the thing the means cannot show — which questions fail consistently and which flicker:

eval/compare.py
    # Which questions fail every time, and which come and go. The first kind
    # is worth engineering against; the second will move on its own.
    tally = Counter()

    for rows in runs:
        tally.update(failures(rows))

    if tally:
        always = [q for q, n in sorted(tally.items()) if n == len(runs)]
        sometimes = [(q, n) for q, n in sorted(tally.items()) if n < len(runs)]

This turns out to be more actionable than any rate. A question failing 7/7 is a bug with a cause you can find. A question failing 3/7 is the model being the model, and time spent on it is time spent on a coin flip.

Try it

One group: mean, range and per-run counts for each signal, plus the fails-every-run and intermittent lists.

9.3Three runs, compare groups, not runs

The rule, in the form it is actually applied:

Lesson
  1. Change one thing. One edit per measured configuration. Two edits and one number cannot be untangled (8.11).
  2. Run it three times, to three named files: OUT=eval/runs/mychange-r1.csv and so on. Never overwrite latest.csv for anything you might want to compare.
  3. Compare groups, never runs. Point compare.py at both sets and believe only REAL.
  4. Engineer against the questions that fail every run. Ignore the flickering ones entirely.
  5. Prefer a steadier instrument to a higher number. retrieval_hit going from “83%, ranging 82–86” to “93%, stable” is two improvements, and the second one is what lets you detect the next change at all.

The cost of this discipline is close to zero here, which removes the last excuse: an eval run is about 120,000 tokens, comfortably inside the free daily bucket for a mini model, and takes a few minutes unattended. There is no reason to compare single runs.

The payoff is visible in the naming of the run files themselves: t1-exact-r1..r3, t1-parser-r1..r3, t2-refactor-r1..r3, t3-progress-r1..r3. Each is a group of three around one change, and each conclusion in this book is drawn from a group.

9.4The baseline belongs to one model

One more constraint that is easy to forget and expensive to forget. retrieval_hit is computed from the citations the model writes. Therefore:

Invariant

The eval baseline is model-specific. Changing LLM_MODEL invalidates every comparison against the recorded numbers, and the baseline must be re-run before any new comparison means anything. The same goes for EMBEDDING_MODEL, which additionally requires the whole index to be rebuilt.

This is not a flaw in the eval; it is an honest consequence of measuring an end-to-end system. But it does mean a number in this book is always a number for a configuration, and quoting it without the configuration is quoting it wrong. Every figure in chapter 7 is openai / gpt-4.1-mini with text-embedding-3-small at 1,536 dimensions, against the corpus dated 2026-09-14.

10Making it pluggable contents

The refactor that split retrieval into two swappable halves. The interesting part is not that it is pluggable — it is where the seam was cut, and how the cut was proved not to have changed any behaviour.

10.1One class doing three jobs

Before: a single QdrantRetriever that did three things.

  1. Turned text into numbers — it held a hardcoded AsyncOpenAI client.
  2. Searched a database — it built Qdrant filter objects directly.
  3. Decided what to keep — the score floor, the cap, the truncation.

That works right up until you want a different database, at which point all three have to be rewritten together, because they are interleaved in one class's methods. And the third job — the policy — is the only one that is actually about this corpus. It is the part you would want to keep unchanged while swapping the other two, and it was the part most entangled with them.

10.2The two sockets

A Protocol is a list of methods with no code behind it. Anything with matching methods satisfies it, with no inheritance and no registration — so GroundedRetriever never learns which store it is talking to. Note dimensions is declared on the Embedder rather than discovered, and the docstring explains why:

retrieval/base.py
class Embedder(Protocol):
    """Turns text into a vector.

    `dimensions` is declared rather than discovered because it has to be
    checked against the index before the first request. Querying a
    1536-dimension index with 768-dimension vectors raises nothing
    anywhere useful - it returns plausible nonsense.
    """

10.3Where the boundary sits, which is the whole design

Two decisions here are the entire value of the refactor, and both are the kind of thing that is obvious in hindsight and easy to get wrong in advance.

1. VectorQuery says what, never how

retrieval/base.py
@dataclass(frozen=True)
class VectorQuery:
    """One search, described without reference to any particular database."""

    vector: list[float]
    limit: int

    #: Keep only provisions that govern this year. None means every year.
    tax_year: int | None = None

    #: Restrict to these section numbers. Used for the exact-lookup path,
    #: where the user named a section and similarity is not the question.
    section_numbers: tuple[str, ...] = ()

Four fields, all of them intent. Nothing about Qdrant's must/should, nothing about IsNullCondition. Each store translates the intent into its own dialect: QdrantStore builds a models.Filter; InMemoryStore evaluates two comparisons in Python; a SQL store would build a WHERE clause. Had the query object carried Qdrant filter objects, writing the in-memory store would have been impossible, and the “abstraction” would have been Qdrant with extra steps.

2. Stores return raw payloads, not domain objects

A store returns Hit(score, payload) where payload is whatever dictionary it stored. It does not return a Passage. Exactly one method in the whole service knows what the payload keys mean:

retrieval/retriever.py
    @staticmethod
    def _to_passage(hit: Hit) -> Passage:
        """Payload shape is a fact about this corpus, so it is known here.

        A store returns whatever it stored; only this method knows that
        "tax_year_from" and "section_number" mean anything.
        """

The reasoning is the sharpest sentence in the codebase: payload shape is a fact about this corpus, not about the database. So a new store never has to learn what tax_year_from means, and a change to the corpus schema touches one method rather than every store.

Lesson

When you draw an interface, ask which side each fact belongs to. Facts about your data (what fields exist, what they mean) belong on your side; facts about the provider (filter syntax, connection handling, batching) belong on theirs. An abstraction that leaks your schema into every adapter has the boundary in the wrong place, and you will only discover that when you write the second adapter — which is the argument for writing the second adapter immediately.

10.4The registries

Three registries in the project, all the same shape — a dictionary from a name to a factory:

retrieval/stores.py and retrieval/embedders.py
#: name -> factory. A Chroma, pgvector or FAISS store is one class
#: implementing `search`, `verify` and `close`, plus one entry here.
STORES: dict[str, Callable[[Settings], VectorStore]] = {
    "qdrant": _qdrant,
    "memory": _memory,
}

EMBEDDERS: dict[str, Callable[[Settings], Embedder]] = {
    "openai": _openai,
}

Plus VENDORS in the gateway, which is the same pattern applied to chat models. Two properties make a registry better than an if/elif chain:

  • Adding a provider does not edit the code that uses it. One class, one dictionary entry. Nothing in retriever.py, main.py or ask.py changes.
  • An unknown name fails loudly, at startup, and says what the options are.
retrieval/stores.py — create()
def create(settings: Settings) -> VectorStore:
    """Build the configured store, failing loudly on an unknown name."""
    try:
        factory = STORES[settings.vector_store_provider]
    except KeyError:
        known = ", ".join(sorted(STORES))
        raise ValueError(
            f"Unknown VECTOR_STORE_PROVIDER {settings.vector_store_provider!r}. "
            f"Known stores: {known}."
        ) from None

A typo in an environment variable becomes a container that will not start, with a message naming the valid values — rather than a 500 on the first real request in production.

10.5InMemoryStore as proof

InMemoryStore is a list of vectors and a cosine loop. It has no server, no network, no Qdrant dependency, and shares no code with QdrantStore. Its docstring explains what it is for:

retrieval/stores.py
class InMemoryStore:
    """A list of vectors and a cosine loop. No server, no network.

    Used by the tests, and as the proof that `VectorStore` is a real
    boundary rather than Qdrant with extra steps. Linear scan, so it suits
    tens of passages, not thousands.
    """

It earns its place three times over:

  1. It proves the abstraction. If the interface leaked Qdrant concepts, writing this class would have been impossible. Which is exactly why it is worth having — an interface with one implementation is a guess.
  2. It made the retriever testable. tests/test_retriever.py has 8 tests covering the cap, named sections, the year filter, dimension mismatch and store failure, with no network at all. tax-agent went from 0 tests to 27 in that one change, and now stands at 36.
  3. It documents the contract by example. Its _governs method reimplements the null-bound logic in six lines of plain Python, which is a far clearer statement of the rule than the Qdrant filter is.

10.6Adding a provider

The whole procedure, for a store: one class implementing three methods, one registry entry. For an embedder: one class with dimensions, name and an async embed, and one registry entry. The code even nominates the next ones:

retrieval/embedders.py — the comment above the registry
#: A sentence-transformers or Hugging Face embedder would be the next entry:
#: wrap `SentenceTransformer(model).encode` in a class with `dimensions`,
#: `name` and an async `embed`, and run it in a thread so it does not block
#: the event loop. It needs no network at request time, which makes it the
#: cheapest way to run this whole service offline.

That “run it in a thread” is the non-obvious part and the reason the note is there. A local model's encode is synchronous and CPU-bound; calling it directly inside an async handler would block the event loop for its whole duration, so every concurrent request would queue behind it — the same hazard the Retriever protocol warns about (4.2).

The two known sharp edges when swapping either half, both already guarded:

  • The index and the embedder must agree. Text embedded by one model and searched with another returns confident nonsense rather than an error. So changing EMBEDDER_PROVIDER or EMBEDDING_MODEL means rebuilding the index, and VectorStore.verify refuses to start when the dimensions no longer match.
  • Changing the model invalidates the eval baseline (9.4).

11Status streaming contents

Three seconds of silence feels much longer than three narrated ones. POST /ask/stream reports every step as it happens — and deliberately does not stream the answer text, for a reason that is about correctness rather than effort.

11.1Server-Sent Events

SSE is the plain-HTTP way to push updates to a client: one long-lived response whose body is a sequence of event: / data: pairs with a blank line between them. It only goes one way, which is simpler than a WebSocket and is all this needs. The entire implementation is one method:

app/progress.py
    def to_sse(self, event: str = "status") -> str:
        """This step as one Server-Sent Events frame.

        SSE is the plain-HTTP way to push updates to a browser: a long-lived
        response, one `event:`/`data:` pair per update, a blank line between.
        Simpler than a WebSocket because it only goes one way, which is all
        this needs.
        """
        payload = json.dumps({"step": self.name, **self.detail})

        return f"event: {event}\ndata: {payload}\n\n"

Three event names are used: status for each step, result for exactly one final frame carrying the same body /ask returns, and error when something fails.

Two implementation details matter more than they look.

The proxy-buffering headers. A reverse proxy is entitled to buffer a response body and deliver it all at once, which would defeat the entire feature invisibly — the stream would work perfectly in development and arrive as one lump in production:

app/routers/ask.py
        headers={
            # Without these a proxy may buffer the whole response and
            # deliver it at the end, which defeats the point entirely.
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",
        },

The pipeline runs as a separate task. This is the piece that is easy to get wrong. An ordinary await run_pipeline(...) inside the generator would complete all the work before yielding anything, and every step would arrive at the end — correct, useless. So the pipeline is launched as a task that pushes steps onto a queue, and the generator drains the queue:

app/routers/ask.py — _stream(), abridged
    """Server-Sent Events: every step as it happens, then the answer.

    The pipeline runs as a separate task and pushes steps onto a queue;
    this generator drains the queue and writes frames. That is what lets
    the steps leave the building while the work is still going on - an
    ordinary `await` would finish everything before yielding anything.
    """
    queue: asyncio.Queue[Step | None] = asyncio.Queue()
    progress = Progress(queue=queue)

    async def run() -> AskResponse:
        try:
            return await run_pipeline(
                request, retriever, gateway, settings, progress=progress
            )
        finally:
            # Always close the queue, so a failure cannot hang the stream.
            await progress.finish()

    task = asyncio.create_task(run())

The finally is load-bearing. If the pipeline raised and the sentinel None were never queued, the generator would block on queue.get() forever and the client would hang on an open connection. Errors also have to arrive as events rather than as HTTP statuses, because by the time anything fails the response has already begun with a 200 — so the error handler yields an error frame carrying the same error_code vocabulary the JSON endpoint uses.

11.2The nineteen steps

The single most transferable design rule in this feature:

Steps carry facts, not sentences

The retrieved step reports acts, sections, titles and scores. It never says “Found 6 provisions!”. Wording is the UI's business, and changing the wording must not mean changing the service. A client should ignore any step it does not recognise rather than displaying it raw.

That rule has a practical consequence you can see in the repository: eval/watch.py exists as a separate program that turns those facts into readable lines. The presentation layer is 90 lines of Python that the service knows nothing about, and a web UI would be a second such consumer with no service change at all.

11.3One implementation, not two

The obvious way to add streaming is to write a streaming version of the pipeline. That produces two code paths that drift apart, and the drift is invisible until someone notices the two endpoints disagree.

Instead there is one run_pipeline and a null emitter:

app/progress.py
    @classmethod
    def discarded(cls) -> Progress:
        """An emitter that accepts every step and keeps none.

        So the pipeline never asks whether anyone is listening.
        """
        return cls(queue=None)

    async def emit(self, name: str, **detail: Any) -> None:
        if self._queue is None:
            return

        await self._queue.put(Step(name=name, detail=detail))

/ask passes nothing, so run_pipeline builds a Progress.discarded() and every await report.emit(...) returns immediately. /ask/stream passes a listening Progress. There is no if streaming: branch anywhere in the pipeline — and a test asserts that both endpoints return identical answer bodies, so the two cannot silently diverge.

Lesson

This is the Null Object pattern, and the reason to know its name is that it applies far beyond streaming: whenever a feature is optional, prefer a do-nothing implementation of the collaborator over a conditional at every call site. Ten if progress is not None checks are ten places to forget one. And note the cost of the pattern is borne where it belongs — one branch inside emit — rather than spread through the caller.

11.4Why the answer text is not streamed

Token streaming was considered, explained, and skipped by choice. The reasoning is the best argument in the project for thinking about a feature before building it.

The correctness argument. Citations can only be verified once the answer is complete, because a fabricated reference may be in the last sentence. Around two answers in forty try to cite a provision that was never supplied — a measured rate, not a theoretical risk. Streaming the prose would therefore mean showing a reader an invented section and retracting it afterwards. For a system whose entire value proposition is “every claim is traceable”, displaying an untraceable claim and correcting it later is worse than a three-second wait.

The value argument. The model spends most of its time before the first token, then writes about 104 words quickly. Word-by-word delivery would save roughly one second of a three-second request — and the status steps already cover the whole wait, including the long silent part that token streaming would not have covered.

The design left for later. If token streaming is added, the safe shape is releasing a paragraph at a time once its citations check out. Never stream and correct.

Lesson

“Everyone streams tokens” is not a requirement. Ask what the feature is actually for. Here the user-visible problem was an unexplained wait, and the wait was mostly before the first token — so status events solve the real problem completely and token streaming solves a quarter of it while breaking an invariant. Naming the invariant you would have to break is the fastest way to evaluate a feature request.

And this feature, like the refactor, was verified behaviour-neutral: three eval runs before and after, every signal within noise, plus a new test asserting that no frame before verified contains the answer text — the invariant written down as an executable check. tax-agent's test count went from 27 to 36.

12.1Image, container, compose

Jargon
Image
A frozen, read-only snapshot of a filesystem plus a default command — a Python version, the installed packages, your code, and “run uvicorn like this”. It is a build artefact, like a .zip. It does nothing until you run it. Built by docker compose build from a Dockerfile.
Container
A running process started from an image, with its own filesystem view, its own network name, and its own environment variables. You can run three containers from one image; when a container stops, anything it wrote is gone unless it was written to a volume.
Volume
A storage area that outlives the container. qdrant_storage is one, which is why make down keeps your index and only make clean destroys it.
Compose
One file, docker-compose.yml, describing several containers that run together: which image each uses, what environment it gets, which ports are published, what order they start in, and a private network on which they can reach each other by service name. That last part is why tax-agent's configuration says http://llm-gateway:8000 and it just works — llm-gateway is a hostname on the compose network.
ports against expose
ports: "8080:8080" publishes a container port to your machine, so you can curl it. expose: "8000" does not: the gateway is reachable from other containers and from nowhere else. That single line is the security boundary that keeps the model endpoint internal.
Health check
A command the container runs on itself every 30 seconds. The gateway's is a three-line Python script that fetches its own /health; tax-agent's is a wget. Compose then honours depends_on: condition: service_healthy, so tax-agent does not start until the gateway is genuinely answering, not merely started.

12.6The timeout ladder

Both of the first two numbers are set in docker-compose.yml environment blocks rather than in the services' .env files, and that is a deliberate choice: the three numbers only make sense in relation to each other, so they belong where the relationship can be seen and commented:

docker-compose.yml
    environment:
      ENVIRONMENT: development
      LOG_LEVEL: INFO
      # Gemini flash currently returns in 6-21s for these prompts, so 30s
      # timed out roughly a third of calls. Each layer must allow more than
      # the one below it or the outer layer gives up first and reports a
      # timeout from the wrong place: model 60 < gateway 75 < harness 90.
      REQUEST_TIMEOUT_SECONDS: 60

Why the order matters. Suppose the gateway allowed less time than the model request it wraps. The gateway would abandon a call that was still legitimately in progress, and the error would say GATEWAY_TIMEOUT — pointing at the gateway, which is the one component that was working. You would debug the wrong service. Correct nesting means the innermost layer that actually ran out of time is the one that reports it, so the error code names the real culprit.

And the corollary from 8.9: the gateway does not retry timeouts, because one 60-second attempt already consumes its entire 60-second retry budget. The harness retries 504 one layer out, where there is room.

12.8Running it on AWS: the two pieces

Locally, docker compose starts three containers on one machine and lets them find each other by name. On AWS the same job is split between two services, and knowing which does what removes most of the confusion:

ECR — Elastic Container Registry
A private warehouse for images. docker push puts an image in it; nothing runs there. Think of it as Docker Hub that only you can read.
ECS — Elastic Container Service
The thing that actually runs an image. It reads a task definition — which image, how much CPU and memory, which environment variables, which port — and starts a task from it. With Fargate you never see or manage the machine underneath.

Two details catch everyone out the first time.

The task definition is immutable. You do not edit one; you register a new revision and point the service at it. So api-task:3 and api-task:4 are different, permanent objects, and rolling back means pointing at the older number. This is a feature: every deployment is a numbered, inspectable artefact.

Secrets are references, not values. The task definition records where the key lives — an SSM Parameter Store path like /gae/prod/llm-api-key — and ECS fetches it at container start using its execution role. The key is never in the image, never in the task definition, and never in git. Rotating it means overwriting the parameter; no rebuild, no redeploy of the definition.

Jargon

Cross-building. Fargate runs X86_64, and an Apple-silicon Mac is arm64. Build an image natively on the Mac and Fargate pulls it, starts it, and dies with exec format error — the binaries are for the wrong processor. Hence --platform linux/amd64 in the push target, and runtimePlatform declared in the task definition so a mismatch is refused at registration rather than discovered at runtime.

Careful

The gateway has no authentication. Anyone who can reach its port can spend your API credit. On a free tier that is an annoyance; with a paid key it is a bill. Keep the security group restricted to your own address, and keep the service scaled to zero except when you are demonstrating it — which is also what stops it costing about $0.46 a day.

12.9Shipping a new gateway, start to finish

The whole sequence, in the order you run it. Each step is one command.

1. Authenticate Docker against your registry. The login lasts twelve hours.

make ecr-login

2. Build for the right processor and push, under a new tag. Never reuse a tag — a tag you can overwrite is a deployment you cannot roll back.

make ecr-push TAG=v3

3. Check it arrived.

make ecr-images

4. Put the API key in Parameter Store. Single quotes so the shell leaves it alone. This is the only step that touches a secret, and it is independent of the image.

aws ssm put-parameter --name /gae/prod/llm-api-key \
  --type SecureString --overwrite --region ap-south-1 \
  --value 'sk-proj-...'

5. Register a new task definition revision from the JSON kept in the repository, so the deployment is versioned alongside the code rather than clicked into a console.

aws ecs register-task-definition \
  --cli-input-json file://deploy/ecs/api-task.json \
  --region ap-south-1 --query 'taskDefinition.revision' --output text

6. Point the service at that revision and start one task.

aws ecs update-service --cluster firstCluster --service api-task \
  --task-definition api-task:4 --desired-count 1 --region ap-south-1

7. Watch it come up. Repeat until running reaches 1; it takes a minute or two.

make ecs-status

8. Confirm the configuration it actually resolved. This is the step people skip, and it is the one that catches a stale environment variable — a leftover LLM_BASE_URL pointing at the old provider, for instance.

aws logs tail /ecs/api-task --region ap-south-1 --since 10m \
  --filter-pattern "vendor resolved"

You want the vendor, model and base URL in that line to be the ones you intended. If they are not, the image is fine and the task definition is wrong.

9. Turn it off. Fargate bills while a task runs.

make ecs-stop
Lesson

There is no load balancer here, so each task gets a fresh public IP and the address changes on every deploy. That is fine for a demo you switch on for an interview, and wrong for anything permanent — the fix is a load balancer with a stable name, which also gives you somewhere to terminate HTTPS.

Notice how little of this touches the image. Steps 4 through 8 are all configuration. The image is one immutable thing; everything that varies between environments lives outside it. That separation is why the same backend:v3 can serve OpenAI or Gemini with no rebuild.

13Known limitations and what is next contents

Two questions fail every run, one fabricates every run, and one planned comparison has never been possible. All four are understood, which is the useful state for a limitation to be in.

13.1SM-01 and SM-02: no cross-Act mapping

The two remaining stable failures are the section-mapping questions:

  • SM-01 — “Section 80C of the 1961 Act corresponds to which section of the 2025 Act?”
  • SM-02 — “Which provision of the 2025 Act replaces section 80D on health insurance premium?”

And here is the important part: these are not retrieval failures. After the named-section lookup, the model now gets s.80C handed to it correctly, reads it, and honestly reports that the provisions contain no statement of correspondence — because they do not. The grader notes confirm it: SM-01 was graded correct (“retrieval never supplied 80C or 123; declining was the correct response to what it had, rule 2”) and SM-02 too (“honest and precise: noted 80D was supplied but the 2025 equivalent was not”). The system is behaving correctly. The corpus cannot answer the question.

The maps_to_1961 column exists in the schema and is populated for 4 of the 552 2025-Act sections, because only a handful of 2025 titles carry the explicit “[S. … of the 1961 Act]” pointer that the parser captures.

Two ways out, both identified:

  1. Fill the column by title matching. The titles match almost exactly across the two Acts — “Deduction in respect of health insurance premia” is 80D in 1961 and 126 in 2025. A title-matching pass in the corpus builder would populate most of the 552, and the payload already carries the field, so retrieval and prompting would need no change.
  2. A runtime second query. When a question asks for a mapping, take the named section's title and run a second search for its counterpart in the other Act.

The first is clearly better: it is a one-off offline computation, it is inspectable in SQLite before it ever reaches the index, and it adds no latency to a request. The second would put a second embedding call — the expensive part (4.10) — on the request path.

Lesson

“The retrieval is wrong” and “the corpus cannot answer this” look identical in a score and need completely different work. Distinguishing them is what the grader notes are for, and it is the difference between two days of retrieval tuning that cannot possibly succeed and an afternoon of title matching that will. Before optimising a retriever, confirm the answer is in there.

13.2PR-06: the fabrication that remains

PR-06 (“which return form applies to a company?”) invented a source in all three of the latest runs. Its root cause is the corpus bug of 8.4: the ITR-6 label genuinely is not in company-ay1.txt. The model retrieves the right pages, cannot find the form number, says so — and then cites DEPT-GUIDANCE s.company-ay3, a page that does not exist.

The grader note captures both halves: “the core conclusion is admirably honest — the form number genuinely is missing from the corpus — but it invented a page to cite”.

The fix is the re-scrape, and it fixes the fabrication as a side effect: a model that can find the label has no reason to invent a page. The fabrication is a symptom of the gap, not an independent defect. Until then the containment holds — the invented reference never reaches citations, and no_fabrication counts it every run.

13.3The A/B against ita_naive that has never run

eval/PLAN.md says the eval should run against both ita_sections and ita_naive, and that “the gap between them is the result that goes in the README”. That would be the strongest single claim the project could make: here is what section-aware chunking with citable metadata is worth, in points, against a conventional fixed-size-chunk baseline.

It has never been possible, for three concrete reasons:

  1. Only ita_sections exists in Qdrant.
  2. /ask has no collection parameter, so there is no way to point a run at a different index without changing configuration and restarting.
  3. make index-naive indexes the 2025 Act PDF only — no 1961 Act, no guidance — so even if it were built it would not be a fair comparison. The naive collection would fail every 1961-Act question for lack of data rather than for lack of structure.

All three are small pieces of work, and they are worth naming precisely because the comparison is the project's headline result waiting to be measured. Note also that naive chunks carry no section_number, so they cannot be cited at all — which means retrieval_hit, computed from citations, would be 0 by construction. A fair A/B would have to score retrieval by inspecting passage text rather than citations, which is a fourth piece of work and the reason this is a project rather than a config change.

14.3The ten lessons, one line each

  1. Put safety in the control flow, not the prompt. Retrieve nothing and the model is never called; cite nothing and the answer is discarded. A guarantee beats a request. — 5.1
  2. A single run cannot settle a small difference. Seven near-identical runs gave retrieval_hit anywhere from 75% to 86%. Three runs, compare groups, engineer only against what fails every time. — 9
  3. One change per measured run. Two changes and one number cannot be untangled; four runs were spent proving that. — 8.11
  4. Ground truth is code and has bugs, and an expectation that can only be met by bad behaviour is worse than no expectation. Check the expectation before the system. — 8.8
  5. The instrument is a second system that can break. Four of the fifteen failures were in the eval, the parser, or the viewer — and they masqueraded as failures of the service. — 8.15
  6. Vector search cannot find an identifier. A number the user typed is an exact-match problem; give it an exact lookup. — 8.5
  7. Relevance is not diversity. Ranking by score alone lets one section take the whole window; a hard cap on the obvious grouping key gets most of what MMR would. — 8.6
  8. Measure before optimising, then believe it. The model call is 95–97% of the request and it is time-to-first-token, so there is nothing to win in retrieval — the right move was to make the wait legible, not shorter. — 4.10
  9. Fail at startup, loudly, with the valid options. An unknown provider name or a dimension mismatch should fail a health check, never produce plausible nonsense at request time. — 3.4
  10. A refactor with no number behind it is hope. Three runs before, three after, every signal within noise and the fails-every-run set identical — that is what behaviour-neutral means. — 10.7

And the one that sits underneath all ten: this system's characteristic failure is producing less, silently. Not a crash, not gibberish — a fluent, well-cited, plausible answer missing a third of the law. Nothing catches that except a set of questions whose complete correct answers you wrote down in advance.

14.4The project in one paragraph

A grounded question-answering service over the Indian Income-tax Acts of 1961 and 2025, which both remain in force for different financial years and which use the same section numbers for different law. Three containerised services — Qdrant for vectors, an llm-gateway that is the only component making a chat call, and a tax-agent that owns retrieval, grounding and refusal — plus a local-only corpus builder that turns two published PDFs and seven department guidance pages into 3,286 citable chunks. Retrieval filters by the tax year the question is about, so the wrong Act cannot reach the prompt; an exact-lookup path handles section numbers, which embeddings cannot; and a per-section cap stops one provision filling the window. Refusal is structural rather than a model judgment: retrieve nothing and the model is never called, cite nothing and the answer is discarded. Both halves of retrieval sit behind Protocols with registries, so either can be swapped by configuration and an in-memory store proves the boundary is real. Everything is measured by a 40-question evaluation harness with six signals, five automatic and one graded by hand against the corpus rather than against real-world tax law; a companion tool compares groups of runs and marks a difference real only when the ranges do not overlap, because the measured run-to-run noise band is eleven percentage points wide. Baseline to now: twelve failing questions down to two, and the two that remain fail because the corpus contains no cross-Act mapping — which is a data problem with a known fix, not a retrieval problem.
